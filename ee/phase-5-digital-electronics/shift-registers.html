Shift Registers — 74HC595 & 74HC165

A shift register turns 3 pins on your MCU into 8 (or 80, or 800) addressable outputs — or 8 inputs into 3 pins back. The 74HC595 is a serial-in/parallel-out (SIPO) "output extender"; the 74HC165 is parallel-in/serial-out (PISO) "input extender." Daisy-chain them and you can drive 64 LEDs from 3 pins, read 32 buttons from 3 pins, or — combined — bridge a 7-segment display, an LED matrix, or a button bank to any MCU. Watch the data bit travel through 8 internal flip-flops on each clock pulse; tap LATCH to commit; see all the outputs change at once.

How the 74HC595 works internally

Eight D-FFs are connected in series. The first FF's D input is the chip's "SER" pin; each subsequent FF's D is the previous FF's Q. All FFs share a single clock (SRCLK / SHCP / CLK — names vary by datasheet). On each rising edge of CLK, every FF samples whatever's at its D input. So the bit at SER advances by 1 position each clock.

After 1 CLK: bit-0 moved from SER to FF0. FF1..FF7 still have whatever was there. After 8 CLKs: 8 new bits have entered, 8 old bits have shifted out the top (overflow to Q7' / chain). The "shift register" output (Q0..Q7) reflects the shift FFs in real-time — every clock changes the visible byte. The "storage register" (Q0..Q7 of the chip) is a separate set of 8 FFs that latch the shift register on the rising edge of RCLK (latch / STCP). → This is why you shift in 8 bits with CLK ticking, then pulse LATCH once to copy them to the outputs all at once — no glitches on the visible outputs while shifting.

How the 74HC165 works (the dual)

Eight parallel inputs A..H feed into a row of 8 muxed FFs. When PL/SH (load) is LOW, the FFs are loaded from the parallel inputs (synchronous load). When PL is HIGH and you pulse CP (clock), the FFs shift their contents toward the QH pin (the top). You read 1 bit per clock — sample, shift, sample, shift, until you've extracted all 8.

PL LOW: each FF loads from its parallel input pin (overrides any previous shift state). PL HIGH, CP rises: each FF samples its previous (lower) neighbor; FF0 samples DS (serial in, or chain previous chip's QH). 8 clocks: 8 bits read out at QH, MSB first. → Read sequence: assert PL, pulse low, deassert; then pulse CP 8 times while reading QH each time.

Daisy-chaining

Both '595 and '165 have a serial output for chaining. On the '595: Q7' (also called QH'). This is the same data as Q7 but available before the latch. Wire Q7' → SER of the next '595, share CLK and LATCH between all chips. Now 16 shifts give you 16 outputs. 100 shifts give you 100 outputs. Limited only by the time you can afford and the propagation delay across the chain.

Total time for N bytes: 8N clocks · period of clock + 1 latch pulse. At 10 MHz (Pico SPI), that's 100 ns/clock × 8 bits = 800 ns per byte → 1.25 MB/s on a chain.

Worked example — 16-LED display from a Pico

The setup

Drive 16 LEDs in a status array from a Pico's SPI peripheral. Use 2× 74HC595 chained. Pico SPI at 10 MHz, with each LED a 5 mA load through a 1 kΩ resistor.

The wiring

Pico SPI MOSI → '595 #1 SER Pico SPI SCK → '595 #1 SRCLK (and '595 #2 SRCLK) Pico GPIO (any) → '595 #1 RCLK (and '595 #2 RCLK) — the LATCH '595 #1 Q7' → '595 #2 SER (daisy chain) '595 #2 Q0..Q7 → LEDs 9..16; '595 #1 Q0..Q7 → LEDs 1..8

The protocol

Send byte 2 (LEDs 9-16): SPI write 0xAA at 10 MHz → 0.8 µs Send byte 1 (LEDs 1-8): SPI write 0x55 → 0.8 µs Latch: pull RCLK high then low → ~100 ns Total update: 1.7 µs → can refresh at > 580 kHz

Why send byte 2 first?

The first byte you send ends up in '595 #1 (closest to MCU); the second byte is pushed through to '595 #2 (farthest). So to map "LED 9" to Q0 of '595 #2, you send the byte for '595 #2 first.

Worked example — reading 8 buttons via 74HC165

The setup

Game controller: 8 momentary buttons + dpad (4 more) = 12 buttons. Use 2× 74HC165 chained, polled at 200 Hz.

The wiring

'165 #1 parallel inputs A..H = buttons 1..8 (each with 10 kΩ pull-up; press = LOW) '165 #2 parallel inputs A..D = dpad (with pull-ups); E..H = N/C '165 #1 QH → '165 #2 DS (chain) MCU SPI MISO → '165 #2 QH (read out) MCU CLK → both chips' CP; MCU GPIO → both chips' PL (active low)

The polling code (pseudo)

while True:
  PL.write(0)                 # load parallel inputs
  PL.write(1)                 # ready to shift
  byte1 = spi.read(1)         # bits from '165 #1 (the higher chip)
  byte2 = spi.read(1)         # bits from '165 #2
  process_buttons(byte1, byte2)
  delay_ms(5)                 # 200 Hz polling rate
Each poll: 0 → 1 latch (0.1 µs) + 16 SPI clocks at 1 MHz = 16 µs total. Easily fits in 5 ms.

What to notice

  • Shift in then latch — never mid-shift. If you latch while shifting, you'll get half-old-half-new outputs flickering. Always complete the byte first.
  • MSB first or LSB first? 74HC595 is MSB-first by convention — the first bit sent ends up at Q7 (after 8 shifts). MCU SPI peripherals typically also do MSB first; align them.
  • SRCLR vs OE. SRCLR clears the shift register (74HC595 specifically); OE (output enable) tristates the parallel outputs. Wire OE low for active outputs; use OE as a "blanking" PWM for software brightness control.
  • 74HC vs 74HCT vs 74AHC. HC = CMOS V_CC 2-6 V. HCT = TTL input thresholds (V_IH=2V) at 5V supply. AHC = faster, lower current. For Pico (3.3V) → ATmega (5V) cross, '74HCT595 at 5V accepts the 3.3V signal cleanly.
  • Use a small filter cap on the latch line if you see glitches. 100 pF is sufficient. The cap absorbs any ringing during the rising edge.
  • Q7' delay is FF-to-FF, not zero. At max clock rate on a long chain, propagation can pile up. Datasheet quotes 18 ns typical at 5V; 30 ns over 12 chips is ~360 ns extra delay.
  • 74HC595 outputs ±6 mA max. For LED driving at 20 mA, use a transistor or LED driver (TLC5940, MAX7219).

Where shift registers show up

Real uses

  • LED matrices — 8×8 or 16×16, driven by 2-4 daisy-chained '595s.
  • 7-segment displays — multi-digit displays: one '595 per digit + transistor drivers.
  • Button arrays — game controllers, keyboards, key matrices, all using '165s.
  • Bit-banged peripherals — driving relays, motors, lights from a budget MCU with only 3 free pins.
  • Cascade JTAG / SPI flash programmers — multi-chip programming via single SPI bus.
  • Inside MCUs — JTAG TDI/TDO is a giant shift register; UART has both a PISO transmit shift register (parallel byte → serial out) and a SIPO receive shift register (serial in → parallel byte); SPI is a shift register.
  • Pseudo-random number generators — LFSRs are shift registers with XOR feedback.
  • Industrial digital I/O modules — 16-32 channel cards with '595/'165 banks + opto-isolation.

  • Q7' = serial out (chain to next SER)

COMMON PITFALLS

  • Floating OE — outputs tristate; downstream sees garbage. Always tie OE low (or to a GPIO).
  • Forgetting SRCLR — after power-on, shift register contains random bits; pulse SRCLR low or shift in 0s.
  • Backwards byte order in chain — first byte sent ends up at LAST chip. Plan accordingly.
  • Latch glitches with mid-shift LATCH pulse — never overlap LATCH with SRCLK.
  • Sourcing too much current — 8 LEDs at 20 mA = 160 mA, way over the 70 mA chip max. Use transistors or specialized drivers.
  • Forgetting OE for blanking PWM — using OE as PWM lets you software-dim without overhead. Don't tie it fixed low if you might want this later.
