USB Enumeration

Plug in a USB device and 50–500 ms later, your OS shows "Device ready." Between those moments is a precisely-choreographed dance of voltage, current, RESET pulses, and descriptor exchange. The host detects the device's pull-up, allocates an address, asks "who are you?" via control transfers, loads a driver, and finally turns on the device's endpoint. Step through each phase below; see exactly which packets fly on D+/D-, when the device draws 100 mA vs 500 mA, and what causes the dreaded "USB device descriptor request failed" error in Device Manager.

ENUMERATION SEQUENCE

1. VBUS apply (plug in)
Host applies +5 V on VBUS to device's connector. Host capacitance: max 10 µF. Device starts up its internal regulators.
2. Initial 100 mA allowance
USB spec: 1 unit load = 100 mA (USB 2) or 150 mA (USB 3). Device must draw < this until configured.
3. Connect: device asserts D+ pull-up
Full-speed device pulls D+ to 3.3V via 1.5 kΩ. Host sees D+=H, D-=L → "Full-speed device attached".
4. RESET (10-20 ms)
Host drives both D+ and D- low simultaneously (SE0 condition) for at least 10 ms. Device responds by initializing all internal state and adopting default address 0.
5. GET_DESCRIPTOR(Device, first 8 bytes)
Host sends SETUP packet on endpoint 0: bmRequestType=0x80, bRequest=0x06, wValue=0x0100 (descriptor type DEVICE, index 0), wIndex=0x0000, wLength=0x0008. The host only needs the first 8 bytes here so it can read bMaxPacketSize0 (offset 7) and learn the real EP0 packet size for the rest of enumeration. Windows/Linux may request more (often 64) and short-packet after the device returns its actual descriptor length.
6. RESET (again)
After learning EP0 max packet size, host resets again to ensure clean state. ~10 ms more.
7. SET_ADDRESS(N)
Host: SETUP bmRT=0x00, bR=0x05, wValue=N (1-127). Device ACKs at addr 0; from now on, listens on address N.
8. GET_DESCRIPTOR(Device, all 18 bytes)
Now using new address. Returns full 18-byte device descriptor: VID, PID, USB version, device class, max EP0 packet, # configurations.
9. GET_DESCRIPTOR(Config, ...)
Host fetches configuration descriptor (9 bytes) → reads wTotalLength → fetches full descriptor (incl. all interface/endpoint descriptors). Class-specific (HID, CDC, MSC) follow.
10. Driver match & load
Host OS matches VID/PID and bDeviceClass/bInterfaceClass to a driver. Linux: udev rules + kernel modules. Windows: INF + WHQL signed driver.
11. SET_CONFIGURATION(1)
Host: SETUP bmRT=0x00, bR=0x09, wValue=1. Device now activates its endpoints. May draw up to bMaxPower (×2 mA) of current from VBUS — up to 500 mA for USB 2.0.
12. Device ready
Endpoints active. Application I/O can begin. Total time: typically 100–500 ms.

D+/D- voltage states and what they mean

HLJ (idle)KFS: idle/mark — line at rest; LS: opposite (K)
LHKJ (idle)FS: opposite of idle; LS: idle
HHSE1SE1illegal — never asserted by spec

Full speed and low speed swap the J/K convention so the receiver's idle (J) is always whichever line has the pull-up. The host detects which by checking which line is HIGH before the first RESET: D+ HIGH → full-speed; D− HIGH → low-speed.

Why enumeration sometimes fails

"USB Device Descriptor Request Failed" (Windows): device's EP0 didn't respond, or stalled. Causes: USB stack bug (bMaxPacketSize wrong), firmware not running (bootloader stuck), VBUS not detected, pull-up not attached. "Unknown USB device": enumeration completed but no matching driver — wrong device class / vendor PID not recognized. Slow enumeration (5+ s): too many retries. Host gives up after N attempts; common cause is EP0 returning malformed data. "Cannot start (Code 10)": SET_CONFIGURATION succeeded but device's class driver failed to claim interfaces. Mismatched CDC-ACM descriptor is the classic. VBUS droop: device tried to draw > 100 mA before SET_CONFIGURATION. Host detects undervoltage and resets — endless re-enumeration loop. → Always use Wireshark + usbmon (Linux) or USBlyzer (Windows) to capture the actual control transfers.

What to notice

  • Two RESETs, not one. The first RESET puts the device into a clean state at address 0; the second confirms the EP0 max packet size before the host commits to using it.
  • Enumeration is host-driven entirely. The device is passive — it only responds. This makes USB extremely predictable but also brittle: any stuck device blocks the host.
  • VBUS = 5 V, but data lines are 3.3 V. Don't drive D+/D- with 5 V logic — fries the host.
  • Speed detection happens before RESET. Host checks the idle state of D+/D- (which line is high) immediately after VBUS settles, before any traffic.
  • High-speed devices look full-speed first. They pull up D+ (full-speed indication), then during the first RESET, they "chirp" K-J-K-J on D-/D+ to indicate HS capability. Host responds in kind; device removes pull-up; both run at HS.
  • The host can refuse SET_CONFIGURATION if total bus power would exceed available budget. USB 2 hubs are limited to 500 mA per port from upstream.
  • String descriptors are optional — iManufacturer = 0 means "no string". Many embedded devices omit them to save flash.
  • VID/PID is the unique identifier for driver matching. Don't pretend to be someone else's VID — license one from USB-IF ($5000) or use a free shared range like FTDI's reseller program.

STEP RECAP

  • VBUS apply → 100 mA limit
  • Device pull-up → speed detected
  • RESET (10 ms) → addr 0
  • Get device descriptor (8 B)
  • RESET → addr 0 again
  • Set address N → device responds
  • Get full device + config descriptors
  • Driver match by VID/PID/class
  • Set configuration → bMaxPower granted
  • App I/O begins

COMMON PITFALLS

  • Drawing > 100 mA before SET_CONFIG — host yanks VBUS.
  • Wrong bMaxPacketSize0 — host's second transfer fails.
  • Stalled EP0 during enumeration — "USB Device Descriptor Request Failed".
  • Malformed config descriptor — class driver won't bind.
  • Same VID/PID across devices — driver loads wrong device.
  • iSerial omitted but app needs it — udev can't disambiguate devices.
  • HS chirp timing wrong — falls back to FS unintentionally.
  • Hub re-enumeration loop — caused by power-glitch + reset combo.
