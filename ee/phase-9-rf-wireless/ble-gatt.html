BLE GATT & Advertising

Bluetooth Low Energy reaches devices in two phases: advertising on three known channels announces the device, then connection hops across 37 data channels for the actual data exchange. The data model — Services, Characteristics, Descriptors — is GATT (Generic ATTribute profile). This visual maps both layers: the 2.4 GHz channel plan, advertising packet format, the GATT tree, and how connection parameters set power vs latency.

2.4 GHz channel plan

BLE uses 40 channels of 2 MHz each from 2402 to 2480 MHz. Three are reserved for advertising: index 37 at 2402 MHz, index 38 at 2426 MHz, index 39 at 2480 MHz — placed in the gaps between WiFi channels 1 (2412), 6 (2437), and 11 (2462) to dodge dominant WiFi traffic. The remaining 37 channels carry data after a connection forms.

GATT Tree — services, characteristics, descriptors

Every BLE peripheral exposes a tree:

SERVICE: Generic Access  UUID 0x1800 (mandatory)
  CHARACTERISTIC: Device Name  UUID 0x2A00, READ
  CHARACTERISTIC: Appearance  UUID 0x2A01, READ
SERVICE: Heart Rate Service  UUID 0x180D (standard, SIG-assigned)
  CHARACTERISTIC: Heart Rate Measurement  UUID 0x2A37, NOTIFY
    DESCRIPTOR: Client Char Config (CCCD) — enables NOTIFY
  CHARACTERISTIC: Body Sensor Location  UUID 0x2A38, READ
SERVICE: Vendor-Specific  UUID 128-bit random
  CHARACTERISTIC: Telemetry  128-bit UUID, READ/NOTIFY/WRITE

Three permission types per characteristic:

  • READ — central can fetch the value at any time. One-shot.
  • NOTIFY / INDICATE — peripheral pushes new value when it changes. NOTIFY is unacknowledged (fast), INDICATE has handshake (reliable).
  • WRITE / WRITE_WITHOUT_RESPONSE — central sends data to peripheral.

Worked example — heart rate monitor

Use case

HRM band worn on chest. Connection interval set to 1 second to extend battery. Heart-rate samples are sent via NOTIFY on the Heart Rate Measurement characteristic.

Connection parameters

Connection interval = 1000 ms (1 Hz heartbeat) Slave latency = 4 → effective heartbeat = 1000 × (1+4) = 5 seconds. Peripheral can skip 4 connection events if nothing to send. Supervision timeout = 30 seconds. Must be ≥ 6 × effective_heartbeat = 30 s. OK. Result: peripheral wakes once per second when active (HR sample), every 5 s when idle. 50× longer battery vs always-on 20 ms.

GATT operations during a sample

1. Peripheral wakes 1 s after last connection event 2. ACK previous data, send NOTIFY (HR value), receive response 3. Sleep until next connection event Total airtime: ~500 µs per second = 0.05 % duty cycle

Common pitfalls

  • Connection interval too short → battery dies fast. 7.5 ms is fastest possible; 50 ms is a good sensor compromise; 1+ s for low-power telemetry.
  • Slave latency without supervision timeout adjustment — increasing latency without proportionally extending timeout causes premature disconnects.
  • NOTIFY without CCCD enable — central must write the CCCD descriptor to enable notifications. Forgetting this is the #1 "peripheral isn't sending data" bug.
  • 128-bit vendor UUIDs — these are 16 bytes vs 2 for SIG-standard. They take more advertising payload. Use SIG-standard UUIDs when possible.
  • Pairing vs bonding — pairing is a one-time encrypted key exchange; bonding stores the keys for later reconnects. Pair without bond = re-pair every connection.
  • Long-Range / Coded PHY — BLE 5+ supports 125 kbps coded PHY for ~4× range. Lower data rate but better link budget; pick per use case.

Worked example — battery-powered fitness tracker

Use case

Heart-rate monitor wristband, CR2032 battery (220 mAh, 3 V). Sends HR sample every 5 seconds; activity update every minute. Target battery life: 6 months.

Connection-parameter tuning

Connection interval: 200 ms — fast enough that HR ack feels live but not wasteful
Slave latency: 24 → effective heartbeat = 200 ms × 25 = 5 s (peripheral skips 24 events when nothing to send)
Supervision timeout: 32 s (must be ≥ 6 × eff_heartbeat = 30 s; 32 s safe margin)
PHY: 1 Mbps (default) — Coded PHY would extend range but 2× current draw

Battery math

Active TX/RX current: 8 mA for ~1 ms per HR sample
Active charge per sample: 8 mA × 1 ms = 8 µA·s
Sample rate: 1 per 5 s → avg active current = 8 µA·s / 5 s = 1.6 µA
Sleep current (RTC + LDO + flash): 5 µA
Total avg current: ~7 µA
Battery life: 220 mAh / 0.007 mA = 31000 h = 3.6 years (theoretical, with 50% derating: 1.8 years)

Comparison: bad connection interval

If we used 30 ms connection interval with latency 0 → wakes 33×/sec instead of 0.2×/sec. Current = 8 mA × 33 = 264 mA·ms/sec = 264 µA. Battery life: 220/0.264 = 830 h = 35 days. The connection-parameter choice is 50× more important than radio efficiency.

Pairing, bonding, and security

BLE security has evolved across versions. Important to pick the right level:

MethodSecurityUse case
Just WorksEavesdropping protection only; MITM-vulnerableToys, basic IoT
Passkey Entry6-digit code displayed on one device, entered on other — MITM-resistantKeyboards, locks
Numeric ComparisonBoth devices show 6-digit code; user confirms matchPhones pairing with smart-home devices (most common)
OOB (Out-of-Band)NFC tap or QR code transfers key — strongestMedical, high-security
LE Secure Connections (BLE 4.2+)ECDH key exchange P-256, FIPS-gradeAll modern apps

Bonding stores the key for later reconnects. Without bonding, devices re-pair every connection — annoying user experience.

Common pitfalls (extended)

  • WiFi co-existence — 2.4 GHz radio inside the same chip needs careful interleaving. BLE adv channels (37/38/39) at 2402/2426/2480 MHz overlap WiFi channels 1/6/11. Many chips handle this with Adaptive Frequency Hopping or PTA (packet-traffic-arbiter).
  • Antenna near body — wearable trackers have antennas detuned by the wearer's body (mostly water). Use a chip antenna at the band edge or a planar inverted-F antenna (PIFA) designed for body proximity.
  • OTA updates over BLE — slow. BLE 1 Mbps PHY tops out around ~75-90 KB/s application throughput with DLE; a 200 KB firmware update takes 2-3 seconds plus retransmits. The 2 Mbps PHY (BLE 5+) roughly doubles that to ~150-170 KB/s — Bluetooth's goodput ceiling is about 1.37 Mbps per the BLE spec.
  • NRF connect cache — phones cache GATT discovery results. If you change the GATT layout in a firmware update, phones may not see the new characteristics until they un-bond and re-bond.
  • iOS BLE limitations — iOS will throttle connection intervals to its preferred range (15-60 ms typical, 1000+ ms in deep idle). Your firmware may negotiate 200 ms but iOS will renegotiate at any time.

Cheat sheet

KEY NUMBERS

  • 40 channels of 2 MHz
  • 3 adv (37, 38, 39) + 37 data
  • 1 Mbps PHY default; 2 Mbps + Coded available BLE 5+
  • Max payload: 27 bytes per packet (legacy), 251 bytes (extended)
  • Adv intervals: 20 ms - 10.24 s
  • Conn intervals: 7.5 ms - 4 s

GATT ROLES

  • Server: holds the data (usually peripheral)
  • Client: reads/writes/subscribes (usually central)
  • Service: logical grouping (HR, battery, custom)
  • Characteristic: value + permissions
  • Descriptor: metadata (CCCD, format, presentation)

COMMON BUGS

  • Forgetting CCCD enable for NOTIFY
  • Too-short connection interval → battery dead in days
  • Supervision timeout < 6× eff_interval → drops
  • 128-bit UUID where 16-bit would do
  • Pair without bond → re-pair each connection
