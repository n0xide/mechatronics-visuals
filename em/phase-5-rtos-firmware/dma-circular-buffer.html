DMA Circular Buffer

DMA (Direct Memory Access) is a separate hardware engine that copies bytes between memory, peripherals, and memory while the CPU does other work. Configure it once — source, dest, count, increments, mode — and it runs autonomously. Circular mode makes it wrap automatically; half-transfer + full-transfer interrupts let you process old data while new data is filling the second half. Combined, this is the foundation of every glitch-free audio capture, every continuous ADC stream, every multi-megabit UART log.

Circular mode — what it does

In linear (normal) mode, when count reaches zero, the channel disables itself. You have to re-arm it, reload the count, and reset the memory pointer. If samples arrive faster than your ISR can re-arm, you lose them.

In circular mode, when count reaches zero, the channel reloads its initial count and memory address automatically — without CPU intervention. The DMA writes byte N, then byte N+1, ... byte BUF_LEN-1, then jumps back to byte 0, byte 1, ... forever (until you stop it explicitly). Combined with auto-incrementing memory pointer + fixed peripheral pointer, this gives you a continuous, lossless capture stream.

Half-transfer and transfer-complete interrupts

Two interrupt sources per DMA channel:

  • HT (Half-Transfer): fires when the DMA has filled the first half of the buffer (index reached BUF_LEN/2).
  • TC (Transfer-Complete): fires when the DMA has filled the whole buffer (index wrapped from BUF_LEN-1 back to 0).

In circular mode, both fire every cycle: HT at the midpoint, TC at the end. This creates a natural "ping-pong" rhythm. While the DMA is filling the second half, your ISR processes the first half — and vice-versa. As long as the processing takes less time than half a buffer's worth of fresh samples, you keep up indefinitely.

Ping-pong buffer pattern

The half/full interrupt pair gives the "ping-pong" without any extra logic. Here's the canonical pattern in C, for STM32 HAL:

static uint16_t adc_buf[BUF_LEN];  // e.g., 256 entries

void setup(void) {
  HAL_ADC_Start_DMA(&hadc1, (uint32_t*)adc_buf, BUF_LEN);
  // DMA configured for circular mode, HT + TC enabled
}

void HAL_ADC_ConvHalfCpltCallback(ADC_HandleTypeDef *hadc) {
  // First half is ready — process adc_buf[0 .. BUF_LEN/2 − 1]
  process_chunk(&adc_buf[0]);
}

void HAL_ADC_ConvCpltCallback(ADC_HandleTypeDef *hadc) {
  // Second half is ready — process adc_buf[BUF_LEN/2 .. BUF_LEN − 1]
  process_chunk(&adc_buf[BUF_LEN / 2]);
}

Notice: the ISRs only fire after a half is fully populated. The DMA is already filling the next half by the time you start processing. No race conditions; no manual ring-buffer pointer arithmetic; the hardware does it.

Why DMA instead of polling or interrupt-per-sample?

Polling: CPU spins reading the peripheral. Wastes 100 % of cycles waiting. Interrupt per sample: CPU takes ~30 cycles of overhead per IRQ. At 100 kSps, that's 3 M cycles/s of overhead — 3 % of a 100 MHz CPU just for IRQ entry/exit, with no real work yet. DMA + circular + half-full: CPU takes ~30 cycles every BUF_LEN/2 samples. At 100 kSps with BUF_LEN=256: ~780 IRQs/s, ~0.02 % overhead. → Two orders of magnitude lighter. Plus the DMA bus arbiter steals cycles from the CPU only when it has data ready — typically 1–2 cycles per transfer, with no SW intervention.

Worked example — 4-channel ADC sampling for a robot IMU + voltage monitor

The setup

STM32F4 (168 MHz) sampling 4 ADC channels in sequence: 3-axis accel scaled to ±2 g (chan 0,1,2), battery voltage divider (chan 3). Target sample rate per channel: 1 kHz → 4 kHz scan rate. ADC clock = 21 MHz, sampling 84 cycles, 12 bits → ~4 µs/conv, 16 µs/scan.

Buffer math

One scan = 4 halfwords (4 channels × 16 bits). Full buffer holds 20 scans = 80 halfwords = 160 bytes; half-buffer = 10 scans = 40 halfwords. At a 4 kHz scan rate, each half-buffer fills in 10/4000 = 2.5 ms — so half/full callbacks fire at 400 Hz. (If you wanted ~100 Hz callbacks, grow the buffer to 80 scans = 320 halfwords.)

DMA configuration

static uint16_t adc_buf[80];  // 4 channels × 20 samples
hdma_adc1.Instance = DMA2_Stream0;
hdma_adc1.Init.Channel             = DMA_CHANNEL_0;
hdma_adc1.Init.Direction           = DMA_PERIPH_TO_MEMORY;
hdma_adc1.Init.PeriphInc           = DMA_PINC_DISABLE;
hdma_adc1.Init.MemInc              = DMA_MINC_ENABLE;
hdma_adc1.Init.PeriphDataAlignment = DMA_PDATAALIGN_HALFWORD;
hdma_adc1.Init.MemDataAlignment    = DMA_MDATAALIGN_HALFWORD;
hdma_adc1.Init.Mode                = DMA_CIRCULAR;     // the key
hdma_adc1.Init.Priority            = DMA_PRIORITY_HIGH;

The ISR processing

void HAL_ADC_ConvHalfCpltCallback(...) { compute_averages(&adc_buf[0], 40); } void HAL_ADC_ConvCpltCallback(...) { compute_averages(&adc_buf[40], 40); }

Timing budget

10 scans / 4 kHz = 2.5 ms between half/full callbacks (400 Hz event rate). ISR work (averaging 10 scans × 4 channels = 40 sample values): ~80 µs on Cortex-M4 — 80 µs / 2500 µs ≈ 3.2 % CPU load. The remaining 96.8 % is available for control loops, comms, display, etc.

What to notice

  • Circular + half/full = no manual ring management. The hardware reload of count and memory pointer means your firmware never touches the DMA after setup. Bugs in pointer arithmetic are impossible because there is no pointer arithmetic.
  • Mem-incrementing, peripheral-fixed is the standard "stream from a single register into a buffer." If you want the reverse (write a waveform out a DAC), invert the direction and the increments stay the same.
  • Buffer size sets latency, not throughput. A 256-sample buffer at 10 kSps gives 12.8 ms latency before the first half-transfer fires. Smaller buffer = lower latency but more IRQs.
  • Don't memcpy out of the live half while DMA is writing to it. Process the inactive half. If your processing is slow, you can hand the half off to a freertos task via a semaphore.
  • Two-priority systems: STM32 DMA has channel-level priority. Audio output (latency-critical) gets HIGH; logging UART (throughput-only) gets LOW. The bus arbiter sorts it out.

Where you'll see this

Real uses

  • Continuous ADC sampling — IMU, microphone, current sensor, joystick — anywhere a sample stream needs to flow uninterrupted.
  • DAC waveform output — audio playback, function generators, motor drive waveforms.
  • UART/SPI/I²C bulk transfer — large transactions handed to DMA; CPU sleeps during the bus turnaround.
  • Memory-to-memory copies — bulk image rotations, framebuffer ping-pong, FFT scratch buffers.
  • USB endpoint buffers — most USB cores use DMA under the hood to keep up with high-speed traffic.

RULES OF THUMB

  • Buffer size ≥ 2 × worst-case-process-time × sample rate (so the other half finishes filling before yours finishes processing).
  • Always make count even so the half-transfer is well-defined.
  • Use volatile on the buffer or compiler may cache it.
  • Place buffer in uncached RAM for very fast peripherals (DTCM/SRAM2 on STM32H7).
  • One DMA channel per peripheral; don't share.

COMMON PITFALLS

  • Forgetting volatile — compiler caches the buffer in a register.
  • Wrong data size — 12-bit ADC needs halfword, not byte. Buffer halves silently.
  • Cache coherency on M7 — DCache enabled? Must invalidate before read.
  • Half-transfer races — if processing takes longer than half-period, you overwrite during read.
  • Mixing memcpy on the live half — use double-buffering or a separate scratch.
