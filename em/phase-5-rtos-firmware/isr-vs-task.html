ISR vs Task — context, rules, latency budget

Interrupts and tasks live in different worlds. ISRs are short, non-blocking, and run at hardware priority. Tasks do the heavy lifting. The bridge between them is a semaphore or queue.

An ISR (interrupt service routine) runs in hardware interrupt context: the CPU saves the current register state, jumps to the handler, runs it, and returns — all while the RTOS scheduler is locked out. ISRs cannot block (no vTaskDelay, no mutex take, no malloc), cannot use the full FreeRTOS API (only ...FromISR variants), and should be short — measured in microseconds, not milliseconds. The pattern is deferred work: ISR grabs the hardware data, signals a task via xSemaphoreGiveFromISR, and returns. The task does the heavy processing (filter, log, parse). Latency budget for a hard-real-time path is the sum of: interrupt entry latency (CPU saves context, ~12 cycles on Cortex-M4), ISR body, exit latency, full FreeRTOS context switch (~100–200 cycles — PendSV has to save/restore the register file and swap stacks), and the task's processing time. For the arm's 10 kHz current loop, the entire path must finish in <100 µs — and it's usually run inside the ISR with no deferred task, because the deferred-work overhead would blow the budget.

ISR — correct: short, signal, return

void ADC_IRQHandler(void) {
  uint16_t s = ADC1->DR;          // read DR clears flag
  latest_sample = s;              // volatile, atomic 16-bit
  BaseType_t woken = pdFALSE;
  xSemaphoreGiveFromISR(sem, &woken);
  portYIELD_FROM_ISR(woken);
}

~80 cycles. Deterministic. Composable.

ISR — wrong: long, blocking, dangerous

void ADC_IRQHandler(void) {
  uint16_t s = ADC1->DR;
  printf("sample: %u\n", s);      // blocks on UART
  float f = (float)s * scale;     // FPU not saved → corrupt
  xQueueSend(q, &f, 100);         // blocking call illegal
  xSemaphoreTake(mx, 0);           // mutex from ISR — undefined
}

Hangs the system, corrupts FPU state, will pass the bench, fail in field.

What to notice

  • Entry/exit latency is fixed by the chip — Cortex-M4 hardware auto-stacking pushes the 8-register exception frame (~12 cycles entry, ~10 exit). At 168 MHz that's ~70 ns each way. You can't optimize this.
  • ISR body should be measured in dozens of cycles — read peripheral, set flag/post sem, return. Anything iterative or floating belongs in a task.
  • Context switch only happens if you yield — portYIELD_FROM_ISR(woken) is the conditional switch. Without it, the high-priority task you just woke waits until the current task yields anyway.
  • For the arm's 10 kHz loop — slide CPU to 168 MHz, deadline to 100 µs. Even with conservative 80-cycle ISR + 15 µs task body, you have ~80 µs of headroom. That's why ARM Cortex-M4 at 168 MHz is the floor for FOC; M0+ at 48 MHz would miss.
  • "Deferred work" pattern is the standard — ISR: 1) grab data 2) signal 3) return. Task: 1) take sem 2) do real work 3) loop. Decouples interrupt rate from task complexity.
  • NVIC priority levels are inverted — on Cortex-M, lower number = higher priority. configMAX_SYSCALL_INTERRUPT_PRIORITY sets the boundary: any interrupt calling FreeRTOS API must have priority numerically ≥ this value. Priorities lower than the boundary (higher actual priority) cannot use FreeRTOS API but also cannot be preempted by it — useful for emergency-stop interrupts.

ISR RULES (memorize)

  • No blocking — no vTaskDelay, no Take (with timeout > 0).
  • No malloc — pvPortMalloc uses a critical section; double fault risk.
  • No printf — blocks on UART, calls malloc, format machinery is huge.
  • Use ...FromISR variants only.
  • portYIELD_FROM_ISR(woken) at the end if you signaled a task.
  • Mark shared vars volatile.
  • Priority > configMAX_SYSCALL_INTERRUPT_PRIORITY (numerically less than) cannot use FreeRTOS API.

BUGS THAT BITE

  • Forgot volatile — compiler caches in register; ISR write never seen.
  • Multi-byte non-atomic read — read uint32 mid-update → torn value.
  • Forgot portYIELD_FROM_ISR — high-priority task wakes but waits.
  • FPU use in ISR without enabling lazy stacking — corrupts caller's FPU regs.
  • Long ISR holds off other interrupts — IMU sample missed, UART byte lost.
  • NVIC priority set above configMAX — silent illegal-API at runtime.
