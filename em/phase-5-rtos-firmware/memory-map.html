MCU Memory Map

When you compile a C program for an MCU, the linker partitions your binary into sections: code (.text) and constants (.rodata) live in Flash; initialized statics (.data), zero-initialized statics (.bss), the heap, and the stack live in RAM. The heap grows upward; the stack grows downward; if they meet, you've crashed. This visual shows where everything lives and how a stack overflow looks from the inside.

Typical Cortex-M layout

0x0800 0000 ┌──────────────────┐  Flash start
            │ .vectors         │  256 bytes — reset + IRQ handlers
            ├──────────────────┤
            │ .text            │  ← function code
            │   (your code)    │
            ├──────────────────┤
            │ .rodata          │  ← const data, strings
            ├──────────────────┤
            │ .data (init)     │  ← copy source for .data section
            └──────────────────┘
0x2000 0000 ┌──────────────────┐  RAM start (SRAM1)
            │ .data            │  ← runtime-writable initialized statics
            ├──────────────────┤
            │ .bss             │  ← zero-init statics
            ├──────────────────┤
            │ heap             │  ← grows up
            │   ↓ ↓ ↓ ↓        │
            │                  │
            │   ↑ ↑ ↑ ↑        │
            │ stack            │  ← grows down
            └──────────────────┘  RAM end

What startup code does

Before main() runs, the C runtime (the "startup file" — startup_stm32f4xx.s, boot_stage2.S on RP2350) executes these steps:

1. CPU loads the initial stack pointer from address 0x0000 in the vector table. 2. CPU jumps to reset handler at address 0x0004. 3. Reset handler copies .data from Flash to RAM (the linker recorded source and destination). 4. Reset handler zeros out .bss. 5. Reset handler calls C-library init (__libc_init_array) — runs static C++ constructors. 6. → Finally calls main().

If you skip steps 3 and 4 (some bare-metal hobbyists do, by accident), globals have garbage values and statically initialized ints are zero. This is the #1 source of "it worked yesterday" bugs.

Stack overflow

A stack overflow on Cortex-M doesn't usually crash with a clean error. The stack pointer keeps decrementing into whatever's below it — heap, .bss, .data. The CPU happily writes the return address into your global variable. You return from a function and end up jumping to an address that used to be your IMU calibration data.

Symptoms:

  • HardFault after a function returns to a corrupted PC.
  • Globals change "by themselves" as the stack scribbles over them.
  • Heap allocator corruption — malloc bookkeeping bytes get overwritten; the next malloc returns garbage or crashes inside heap_4.c.
  • FreeRTOS task crashes randomly with no clue why.

Defenses:

  • Stack canary: write a known pattern (0xDEADBEEF) at the bottom of the stack at boot; check periodically. If it changed, you've overflowed.
  • MPU region: configure the Cortex-M MPU to fault if the SP goes below its limit. Catches the overflow at the moment it happens.
  • FreeRTOS stack high-water mark: call uxTaskGetStackHighWaterMark() periodically; budget for ≥ 32 words headroom per task.
  • -fstack-usage: GCC flag that emits .su files reporting each function's max stack frame. Sum up the call graph.
  • Static analysis: tools like checkstack compute call-graph depth and report the worst path.

Worked example — diagnosing a HardFault

The symptom

FreeRTOS robot-controller task crashes with HardFault after running for 47 minutes. PC = 0xCAFEDEAD (clearly invalid). LR shows a return into the task's main loop. Same task ran cleanly with smaller buffers.

What to check

UBaseType_t hwm = uxTaskGetStackHighWaterMark(NULL); printf("HWM = %u words remaining\n", hwm);

Result: HWM = 4. Task was allocated 512 words; high-water = 508 used, leaving 4 free. One more interrupt nesting and it would overflow.

The root cause

A new feature added a 1024-byte JSON parser called from inside the task. That's 256 words on top of the existing usage. Adding 256 to 508 = 764, which is well over the 512-word allocation.

The fix

xTaskCreate(robot_task, "robot", 1024, NULL, 5, NULL); // was 512

Or: move the JSON parsing buffer to a static global (out of stack). Or: split the JSON work into a separate task with its own stack.

Verification

Re-run for 4 hours, HWM stays at 200+ words throughout. Done.

What to notice

  • The map file is the source of truth. After every build, arm-none-eabi-objdump -h app.elf or look at the .map file to see exact section sizes. They never lie.
  • Globals are not "free" RAM. Every int my_buffer[1000]; at file scope adds 4 KB to .bss permanently.
  • Stack frames are small in optimized builds. -O0 might use 50 % more stack than -O2 because the compiler doesn't reuse registers across calls.
  • Heap fragmentation kills long-running embedded systems. The total free is fine, but no single block large enough. Prefer fixed-size pools (FreeRTOS heap_4 is mostly OK; heap_5 is better for multi-region).
  • Read the .map after every change. Watching .bss grow by 4 KB tells you a new buffer was added; watching .text grow by 200 KB tells you you accidentally included libc's printf.

Where you'll see this

Real uses

  • Linker scripts — .ld files describe the memory map. Every project has one (auto-generated by IDEs).
  • Stack-overflow detection — FreeRTOS configCHECK_FOR_STACK_OVERFLOW.
  • OTA updates — second app slot at known Flash address, bootloader switches between.
  • DMA buffer placement — STM32H7 cache lines, ESP32-S3 PSRAM, RP2040 SRAM banks — placement decides bandwidth.
  • Crash dumps — capture SP, PC, LR + a chunk of stack, log to flash for post-mortem.

RULES OF THUMB

  • Stack budget per task: 1–4 KB typical; +32 words headroom.
  • Heap fragmentation: avoid malloc/free in tight loops; use pools.
  • printf pulls 20+ KB into .text — use tinyprintf or RTT.
  • DMA buffers must live in DMA-accessible RAM (check on H7/F7).
  • Check uxTaskGetStackHighWaterMark() in tests.

COMMON PITFALLS

  • Skipping startup .bss zero — uninitialized statics are garbage.
  • Heap collision — stack grows into heap silently.
  • Recursive function with no base case — instant blowout.
  • Large stack arrays in ISR — chip-killer.
  • printf with float on F0/F1 — pulls in soft-float, kilobytes.
