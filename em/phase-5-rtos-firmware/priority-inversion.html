Priority Inversion — and inheritance fixes it

High-priority task is blocked by a low-priority task holding a mutex. A medium-priority task, oblivious, runs and runs — for as long as it wants. This crashed the Mars Pathfinder. Twice.

Classic priority inversion: HIGH needs a resource (e.g., shared buffer). LOW is currently holding the mutex for that resource. HIGH blocks. While LOW is running to release the mutex, MED becomes ready and (correctly, by policy) preempts LOW. MED doesn't touch the mutex, so it runs to completion. Meanwhile HIGH sits blocked indirectly behind MED — its priority effectively dropped to LOW's. This bit Mars Pathfinder (1997): the bus-management thread (high) was blocked waiting for the meteorological-data thread (low) to release a pipe; a communications thread (medium) kept preempting the low-priority task; watchdog timed out; system reset. NASA fixed it in flight by enabling priority inheritance on the mutex: when HIGH blocks on a mutex owned by LOW, the scheduler temporarily boosts LOW to HIGH's priority so MED can't preempt it. LOW finishes its critical section quickly, releases the mutex, and drops back to its own priority. HIGH unblocks. The total delay is bounded by LOW's critical-section length, not "however long every MED task feels like running."

Mars Pathfinder, 1997

The bus-management thread (high) needed an IPC pipe owned briefly by a meteorological-data thread (low). A communications thread (medium) kept preempting LOW. HIGH never got the pipe. Watchdog timed out. System reset. Cycle.

Fix: VxWorks had priority inheritance available but disabled by default on that mutex. Flight engineers patched the parameter remotely. Behavior went from "resets every few days" to "no resets in the rest of the mission."

What to notice

  • Switch protocol to "None" — HIGH blocks the moment it requests the mutex. MED then runs to completion while HIGH is supposed to be highest priority. HIGH's effective priority dropped to LOW's, and LOW is itself blocked by MED. That's the "inversion."
  • Switch to "Priority inheritance" — the moment HIGH blocks on the mutex, scheduler boosts LOW to HIGH's priority (shown in dark red). MED can no longer preempt LOW. LOW finishes its critical section, gives the mutex, drops back, HIGH unblocks.
  • The bound matters — with inheritance, HIGH's worst-case block time = length of LOW's critical section. Without, it's unbounded (= sum of all MED-priority work). Bounded latency is the whole point of RT.
  • It's MED that ruins everything — inversion happens because MED can preempt LOW. If only HIGH and LOW exist (no MED), the chain is bounded by the critical section regardless of inheritance.
  • Inheritance is a mutex-only feature — binary semaphores do not implement it; they have no notion of "owner." If you protect a resource with a binary sem, you've built a Pathfinder. Use mutexes.
  • Keep critical sections tiny — even with inheritance, HIGH is blocked for the entire critical section. xSemaphoreTake → update_one_field → xSemaphoreGive, not "take mutex, parse JSON, write to flash, give mutex."

Cheat sheet

BLOCKING BOUNDS

No protocol
B_high = ∞ (unbounded) limited only by how long MED-priority work runs
Priority inheritance
B_high ≤ Σ longest crit-sec of each lower-priority task
Priority ceiling
B_high ≤ 1 critical section stronger guarantee, prevents deadlock too
Response time
R_i = C_i + B_i + Σ ⌈R_i/T_j⌉·C_j over all higher-priority tasks j; iterate to fixed point

PROTOCOLS

  • Priority inheritance (PI) — boost holder to blocker's priority on contention. FreeRTOS mutexes do this. Default for Linux RT, VxWorks.
  • Priority ceiling (PCP/ICPP) — boost holder to max priority of any task that could request the mutex, the moment it's taken. Prevents chained blocking and deadlock.
  • No protocol (sema/flag) — vulnerable to unbounded inversion. Use only for signaling, never resource protection.
  • Lock-free / atomics — no mutex, no inversion. Limited to operations the CPU supports atomically (compare-and-swap).

BUG SIGNATURES

  • "Sometimes the control loop just freezes for a few hundred ms" — classic unbounded inversion. Check what shares mutexes with the loop.
  • Binary semaphore "protecting" a data structure — find it, replace with mutex.
  • Long critical section — printf, malloc, file I/O while holding mutex.
  • Nested mutex with inconsistent order — A→B in one task, B→A in another. Deadlock. Use priority ceiling or one-mutex-only policy.
  • configUSE_MUTEXES = 0 — you have semaphores not mutexes. Inheritance not active.
