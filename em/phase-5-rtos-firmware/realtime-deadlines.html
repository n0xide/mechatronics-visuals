Real-Time Deadlines — hard/firm/soft and schedulability

"Real-time" doesn't mean "fast." It means "consequence-aware about being late." Three flavors of deadline, one schedulability test, and the arm's 10 kHz budget.

A real-time system is one where the value of a result depends on when it's produced, not just whether it's correct. A control loop that computes the right torque 5 ms too late has already shipped destabilizing oscillation to the actuator. "Real-time" doesn't mean "low latency" — a slow RT system is fine as long as deadlines are met. It comes in three flavors. Hard: missing a deadline is a system failure (airbag deployment, FOC current loop, drone IMU). Firm: a missed deadline produces zero value but isn't catastrophic — drop it and move on (a video frame past its display time). Soft: late is worse than on-time, value degrades smoothly (a UI redraw, a logging sample). The whole point of an RTOS is to give you the tools to prove (or at least argue) that hard deadlines will be met. Schedulability analysis — adding up CPU utilization Σ C/T and checking against Liu-Layland's bound for RMS — is the back-of-envelope test. Stay under ~69% and any RMS-prioritized set will meet deadlines.

The three flavors of deadline

HARD

Missing the deadline causes catastrophic failure. The system must always meet it, and the design must prove it (worst-case analysis, formal schedulability).

Airbag deploy. Pacemaker pulse. Arm FOC current loop (10 kHz). Aircraft fly-by-wire.

FIRM

Result has zero value past the deadline but missing is not catastrophic. Late results are discarded. Acceptable to miss a small fraction.

Video frame past display time. Stale sensor sample. Network packet past media-playback window.

SOFT

Value degrades gracefully past the deadline. Late is worse than on-time; very late is worse than mildly late, but still has some value.

UI button response (<100 ms feels instant; 500 ms feels slow but still works). Arm position loop @ 1 kHz (technically firm, often treated as soft). Telemetry upload.

What to notice

  • Default sliders model the arm — T₁=0.1 ms (10 kHz current), C₁=0.04 ms → U₁=40%; T₂=1 ms (1 kHz position), C₂=0.20 ms → U₂=20%; T₃=10 ms (100 Hz comms), C₃=2.0 ms → U₃=20%. Total U ≈ 80%. That sits above Liu-Layland's 78.0% bound for N=3 — schedulability isn't guaranteed by the sufficient test, but a response-time analysis still passes (see worked example below). Pull C₁ down to 0.03 ms (30 µs) and total drops to 70%, comfortably under LL.
  • Bump Task 3's exec to 5 ms — that's a 100 Hz task taking 5 ms per cycle. U₃ jumps to 50%, total to ~100%. Red zone. Real outcome: comms task starves the position loop, robot judders.
  • Bump Task 1 exec to 0.08 ms — the current loop now spends 80% of its 100 µs budget on math. Tiny disturbances (an extra ISR) and you miss the deadline. Healthy margin is 50–60% per task.
  • Liu-Layland is sufficient, not necessary — being above the LL bound doesn't mean you'll miss deadlines, only that the simple test no longer guarantees you. Run a response-time analysis (worst-case completion = own exec + interference from higher-priority tasks).
  • The bound shrinks with N — N=1: 100%, N=2: 82.8%, N=3: 78%, N→∞: 69%. Adding tasks reduces the guaranteed-safe utilization. The fewer tasks at a given utilization, the better.
  • EDF is optimal but tricky — Earliest-Deadline-First can hit 100% utilization. But priority changes at runtime, harder to debug, less common in safety-critical embedded. Fixed-priority RMS dominates the field for a reason.

Liu-Layland test

LL bound for N=3: 3·(2^(1/3) − 1) = 3·0.2599 = 0.780 = 78.0%
U_sum = 65% < 78.0% → schedulable under Rate-Monotonic ✓
RMS assignment: shortest period → highest priority. Under FreeRTOS (higher number = higher priority): current loop = prio N−1 (highest), position loop = prio N−2, comms = prio N−3. Under POSIX/Linux SCHED_FIFO and Cortex-M NVIC: lower number = higher priority, so current = 0, position = 1, comms = 2. Same ordering, opposite numbering.

Response-time analysis (tighter than LL)

Classical RTA solves R = C + Σ ⌈R/Ti⌉·Ci iteratively until R converges. Below we use the upper-bound shortcut: assume interference = D × (higher-priority rate). Tight enough to confirm schedulability when it passes; the iterated fixed-point gives a smaller R when it matters.

Current loop (highest prio): no preemption, R = C = 0.03 ms ≪ 0.1 ms deadline ✓

Position loop: preempted by current loop. Upper bound = own exec + ⌈D/T_current⌉ × C_current = 0.20 + 10·0.03 = 0.50 ms < 1.0 ms ✓ (iterated RTA converges lower, ~0.29 ms)

Comms: preempted by both. R = 1.5 + ⌈10/0.1⌉·0.03 + ⌈10/1⌉·0.20 = 1.5 + 100·0.03 + 10·0.20 = 1.5 + 3.0 + 2.0 = 6.5 ms < 10 ms ✓ (also a shortcut bound)

What kills it

Add a 4th task: encoder filtering at 5 kHz (T=0.2 ms, C=0.04 ms, U=20%). New U_sum = 85% > LL bound for N=4 (75.7%). Response-time analysis still says yes (~75% worst-case for position loop) but Liu-Layland fails. Either accept higher analytical risk or drop the encoder filter rate.

Cheat sheet

FORMULAS

Utilization
U_i = C_i / T_i
Liu-Layland bound
U_bound = N·(2^(1/N) − 1) N=1 → 1.000, N=2 → 0.828, N=3 → 0.780, N=∞ → 0.693
Sufficient test
Σ U_i ≤ U_bound ⇒ schedulable
Necessary test
Σ U_i ≤ 1 (any policy)
Response time
R_i = C_i + Σ ⌈R_i/T_j⌉ · C_j over j higher priority than i; iterate to fixed point

ARM PROJECT BUDGET

  • Current loop — 10 kHz (T=100 µs), C ≈ 40 µs → U=40%, HARD deadline
  • Position loop — 1 kHz (T=1 ms), C ≈ 200 µs → U=20%, SOFT
  • Comms (ROS 2 topic) — 100 Hz (T=10 ms), C ≈ 2 ms → U=20%, SOFT
  • Logging — 10 Hz (T=100 ms), C ≈ 5 ms → U=5%, SOFT
  • Σ U ≈ 85% — over LL bound; need response-time analysis. In practice, current+position on RT MCU, comms+log on SBC.

WHAT GOES WRONG

  • Misjudging C — measured exec time is best-case; worst-case is 2–10× higher due to cache misses, branch prediction, ISR storms.
  • Forgetting interrupt overhead — ISRs steal CPU from every task. Add their utilization too.
  • Counting only RT tasks — context-switch overhead, RTOS tick, idle housekeeping all consume cycles.
  • Treating soft as hard — over-engineering a UI task adds cost; treating hard as soft loses limbs.
  • Σ U > 1 — overload, period. No scheduler can fix this. Reduce work, drop a task, or buy a faster MCU.
