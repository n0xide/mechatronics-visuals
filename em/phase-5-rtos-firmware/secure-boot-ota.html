Secure Boot & OTA — chain of trust + safe field updates

An IoT device in the field is an attack surface. Unsigned firmware lets anyone flash a backdoor. No rollback protection lets attackers downgrade to a known-vulnerable old version. No A/B partitions means a botched update bricks the device. Modern embedded systems solve all three with a secure-boot chain of trust (silicon root key → bootloader → app, each verifying the next), plus an OTA update protocol with A/B partitions, signed manifests, and rollback counters. This visual walks the boot chain, simulates an OTA update with verification + rollback, and breaks down threat models.

The chain of trust

1. ROM bootloader (immutable)Burned at fab; cannot be changedVerifies the secondary bootloader signature with the public key fused into hardware (eFuse / OTP)Root public-key hash in eFuse (one-time programmable)
2. SBL (Secondary Bootloader)Updateable bootloader (rare updates)Verifies the main bootloader / firmware signaturePublic key embedded in SBL (which was itself ROM-verified)
3. Bootloader (e.g., MCUboot)The "loader of last resort" — also handles OTAVerifies application image signature + checks rollback counter + selects A or B slotPublic key embedded in MCUboot binary

Each stage verifies the NEXT one before transferring control. If any verification fails, the chain breaks and the device stays in the previous (known-good) state. The ROM bootloader is the root of trust — its key cannot be changed, so its trust must be absolute (compromised root = compromised device, forever).

A/B partition update flow

Memory map: two equal slots in flash. Slot A holds the running firmware; Slot B receives the new image. Once verified, the bootloader marks B as "primary" and reboots into it. If B fails its boot health check, the bootloader falls back to A.

1. App requests new firmware → download into Slot B (currently inactive) 2. App writes "boot from B (test mode)" flag in non-volatile metadata 3. Reboot. MCUboot: a. Reads metadata → "boot test from B" b. Verifies B's signature against MCUboot's embedded public key c. Checks rollback counter ≥ device's last counter d. If all pass, jumps into B (still in "test mode") 4. New app boots. Within N seconds, it must call mcuboot_image_ok() to confirm health. • If yes: MCUboot promotes B to primary slot, retains A as fallback • If no (timeout or app crashes): next reboot → MCUboot reverts to A 5. (Optional) A is now "next slot" for the following update

Atomicity: every step is restartable. Lose power mid-step → metadata still consistent → bootloader picks up where it left off. No combination of failures leaves an unbootable device.

The rollback counter — preventing downgrade

Without rollback protection, an attacker who finds a vulnerability in firmware v1.0 can: (a) signal your OTA server to deliver "v1.0" again, (b) the device verifies the signature (still valid since you used the same key), (c) installs v1.0, (d) attacker exploits the known vulnerability. Defense: a monotonically-increasing rollback counter stored in OTP / fuses / RPMC.

Each firmware image is signed with a manifest including (version, rollback_counter, image_hash). Bootloader rejects any image with rollback_counter < device.current_counter On successful boot of new image, device increments its counter to match. If rollback counter is in eFuse (OTP), it's truly irreversible. If in regular flash, it's tamper-resistant only — physical attacker with chip-level access could potentially revert.

Worked example — STM32U5 firmware update over BLE

Setup

STM32U585 (Cortex-M33 with TrustZone), 2 MB flash split into 512 KB Boot + 512 KB Slot A + 512 KB Slot B + 512 KB User Data. Firmware ~200 KB. ECDSA-P256 signatures with public key hash burned into eFuse OTP.

OTA download (BLE GATT)

App receives 200 KB firmware in ~244-byte chunks over BLE (~50 KB/s effective at BLE 5 with DLE; ~10–30 KB/s on bare BLE 4.2) Each chunk written to Slot B as it arrives — flash time bounded by BLE throughput, not flash latency; ~4–20 s total at BLE 5 / 5 PHY CRC32 on each chunk for transport integrity (link-layer integrity is also present) After last chunk, app writes "boot-test from B" flag + reboots

Boot-time verification (MCUboot)

1. ROM verifies Boot binary's signature against eFuse public-key hash (~5 ms with HW SHA + ECDSA) 2. Boot reads metadata → "test mode from B" 3. Boot reads B's image-trailer manifest (image_hash + ECDSA signature + version + rollback_counter) 4. Boot computes SHA-256 over Slot B image (~60 ms for 200 KB on M33) 5. Boot verifies ECDSA-P256 signature on (hash || version || rollback_counter) — ~10 ms with HW 6. Boot checks rollback_counter ≥ device.counter (compare two 32-bit words) 7. All pass → jump into Slot B (still in "test mode") Total verify time: ~75 ms — invisible to user

Commit or revert

New app starts. Within 30 seconds it must call mcuboot_image_ok() — typically after passing internal self-test + connecting to MQTT broker If yes: metadata updated, B is primary. Device.counter incremented from N to N+1. If no (app crashes, watchdog resets): next boot → MCUboot reverts to A. App and rollback_counter unchanged. App reports update status (success / reverted) over BLE/cellular at next opportunity.

Common pitfalls

  • Hardcoding the verification key in updateable code — the public key MUST be in immutable storage (ROM / eFuse). If attackers can flash a new MCUboot with their key, they own the chain.
  • Skipping rollback counter — "I have signatures" isn't enough. Attackers can replay older valid versions to exploit known bugs.
  • Boot-test without watchdog — if the new image just hangs (not crashes), the device sits broken until manually reset. Use a hardware watchdog that triggers a revert on timeout.
  • Single-slot update with no recovery — power loss during flash erase = bricked device. Always A/B or have a recovery bootloader.
  • OTA over unencrypted transport — even if the image is signed, exposing the binary lets attackers reverse-engineer your code. Encrypt in transit (TLS, BLE bonded link).
  • SBL / Bootloader is too privileged — if the SBL stays resident, it's a permanent attack surface. Use ARM TrustZone or RISC-V PMP to isolate it; better, exit to non-secure world after boot.
  • Forgetting to clear keys after boot — private signing keys belong on a build server, never on the device. Even ephemeral keys should be wiped after use.
  • Trusting your own crypto — don't implement ECDSA / Ed25519 from scratch. Use a vendor-reviewed library (mbedTLS, wolfSSL, Cifra, libsodium-embedded).
  • OTA server unaudited — most attacks happen at the server, not the device. Sign images in a hardware-security-module (HSM); never let the server-side store the signing key in plain text.
  • Public-key revocation — if your build infra is compromised, every device with that key is permanently vulnerable. Plan a key-rotation scheme (e.g., 2-of-3 quorum keys with hardware HSM).
