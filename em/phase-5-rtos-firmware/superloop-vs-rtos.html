Super-loop vs RTOS

Why a while(1) of function calls collapses the moment one job takes "a little too long" — and what a preemptive scheduler does about it.

A super-loop is the first architecture every embedded engineer writes: while(1){ read_sensor(); update_control(); update_display(); handle_uart(); }. It works perfectly when every job runs faster than the deadline of every other job. It fails the moment one job (LCD redraw, SD card flush, JSON parser) hogs the CPU and your 1 kHz control loop suddenly runs at 200 Hz with 5 ms jitter. An RTOS (FreeRTOS, Zephyr, ThreadX, NuttX) replaces the loop with a scheduler: each job is a task with its own stack and priority, and a hardware tick interrupt (typically 1 kHz) re-evaluates which task should be running. If a higher-priority task becomes ready (semaphore given, queue posted, timer elapsed), the scheduler preempts whatever is running and switches to it. The control loop's deadline survives the LCD redraw because the LCD task runs at a lower priority and gets shoved aside. The cost: context-switch overhead (~few µs), more RAM (one stack per task), and a much more careful conversation about shared data.

What to notice

  • Super-loop period drifts with workload — the control loop fires every time it gets a chance, which is after the LCD finishes. Set LCD to 6 ms and control "1 kHz" becomes ~150 Hz. Worst-case latency = sum of every other job's worst-case time.
  • RTOS preempts mid-LCD — the red ticks in the RTOS row are preemption boundaries: scheduler tick fires, sees control is ready, saves LCD context, runs control, restores LCD. LCD takes longer wall-clock but control hits its deadline every time.
  • Jitter ≠ latency — even when the super-loop "makes it," the time-between-iterations varies wildly. PID loops, filters, and observers assume dt = constant; jitter pollutes derivative terms and ruins gain margins.
  • RTOS overhead is real but tiny — a full FreeRTOS context switch on Cortex-M4 at 168 MHz is ~100–200 cycles ≈ 0.6–1.2 µs (PendSV save/restore of the register file + stack swap). A 1 kHz tick still adds well under 1 % CPU. The cost is RAM (each task needs ≥512 B stack) and discipline (shared data needs mutexes).
  • For the arm: 10 kHz current loop is non-negotiable — that's 100 µs budget per iteration. A 3 ms LCD redraw in a super-loop would miss thirty deadlines. This is why FOC on a multi-job MCU lives in an RTOS task (or, more often, on a dedicated MCU).
  • Cooperative scheduling is a middle ground — Arduino's loop() + yield(), MicroPython's asyncio. Tasks voluntarily yield. Simpler but one runaway task still hangs everything. Useful for UI-heavy systems with no hard-real-time work.

WHEN TO PICK WHICH

  • Super-loop — single job, OR multiple jobs all faster than smallest deadline. Blink LED, read one sensor, dumb actuator.
  • Cooperative (asyncio, Arduino) — UI + IO + slow control. Easy mental model, no preemption hazards.
  • Preemptive RTOS — hard-real-time control loop + slower jobs in same MCU. FOC, IMU fusion, comm stack.
  • Bare-metal ISRs + main loop — only 1-2 fast jobs, both fit in ISRs; main loop does background. Common in motor drivers.
  • Multi-MCU partition — when even an RTOS can't hit the deadline. Dedicate one MCU per loop. (arm-6dof: Pi 5 for MoveIt, MCU for FOC.)

COMMON TRAPS

  • "I'll just add a delay" — delay(10) in a super-loop is a confession that you needed an RTOS three jobs ago.
  • RTOS tick = 1 ms ≠ resolution — tasks waking on tick boundaries have 1 ms granularity. Use hardware timer ISR for sub-ms loops, not vTaskDelay.
  • "It works on the bench" — super-loop timing is data-dependent (JSON parse, SD write). Bench data never exercises worst case.
  • Mixing blocking and non-blocking — one HAL_SPI_Transmit() with a 100 ms timeout will ruin any architecture.
