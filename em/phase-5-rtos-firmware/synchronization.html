Synchronization — mutex, semaphore, queue

Four primitives, four different jobs. Pick the wrong one and you'll either deadlock, corrupt data, or invert priorities.

Multiple tasks sharing state needs ground rules. The four RTOS primitives — mutex, binary semaphore, counting semaphore, queue — solve different problems despite looking similar. Mutex enforces mutual exclusion: only one task holds it at a time, only the owner can release, and the scheduler can boost the holder's priority (inheritance) if a higher-priority task is waiting. Binary semaphore is a signaling flag with no ownership: ISR gives, task takes. Cheaper than a mutex but no protection against priority inversion — use it for events, not resources. Counting semaphore models a pool of N identical resources (N UART buffers, N camera frames). Queue is a thread-safe FIFO of copies — the canonical producer/consumer pipe. ISR captures a sample, posts to a queue, control task receives and processes. The queue does its own locking; the data is copied, so no shared-pointer hazards.

Mutex — mutual exclusion with ownership

Two tasks both want to update a shared position_setpoint. Without a mutex, Task A's "set X=10" might be interleaved with Task B's "set Y=20" mid-struct → torn read. With a mutex, only the holder can write; everyone else blocks.

SemaphoreHandle_t mx = xSemaphoreCreateMutex();

// Task A — controller
xSemaphoreTake(mx, portMAX_DELAY);
setpoint.x = 10.0;          // critical section
setpoint.y = 5.0;           // no preemption mid-struct
xSemaphoreGive(mx);            // only owner can give

Binary semaphore — ISR-to-task signal

ADC end-of-conversion ISR fires. ISR is short — it just posts a flag. The processing task was blocked on xSemaphoreTake; the scheduler wakes it as soon as the ISR returns.

SemaphoreHandle_t sem = xSemaphoreCreateBinary();

// ISR (ADC EOC) — short
void ADC_IRQHandler(void) {
  BaseType_t woken = pdFALSE;
  xSemaphoreGiveFromISR(sem, &woken);
  portYIELD_FROM_ISR(woken);   // switch immediately if needed
}

// Task — does the heavy work
for(;;) {
  xSemaphoreTake(sem, portMAX_DELAY);   // block until ISR signals
  run_filter();
}

Counting semaphore — resource pool of N

Pool of 3 DMA buffers. Up to 3 tasks may hold one. The 4th blocks until someone gives one back.

SemaphoreHandle_t pool = xSemaphoreCreateCounting(3, 3);
// max=3, initial=3 → "3 buffers available"

// Any task that needs a buffer
xSemaphoreTake(pool, portMAX_DELAY);  // count-- (block if 0)
buf = grab_free_buffer();
... fill / use ...
release_buffer(buf);
xSemaphoreGive(pool);                  // count++

Queue — producer / consumer FIFO

ADC ISR posts samples to a 16-deep queue. Filter task reads from queue. If filter is fast, queue stays near 0. If filter slows down (e.g., printf in the loop), queue fills and ISR posts start failing — backpressure signal.

Producer rate: 10/s  |  Consumer rate: 8/s 
QueueHandle_t q = xQueueCreate(16, sizeof(sample_t));

// ISR — producer
xQueueSendFromISR(q, &sample, &woken);

// Task — consumer
sample_t s;
xQueueReceive(q, &s, portMAX_DELAY);   // blocks if empty
process(s);

What to notice

  • Mutex has an owner; semaphore does not — only the task that took the mutex may give it. Any task or ISR can give a semaphore. Confusing the two is the #1 RTOS bug.
  • Never call mutex_take from an ISR — ISRs cannot block. Use xSemaphoreGiveFromISR with a binary semaphore to signal a task; let the task own the mutex.
  • Queues lock themselves — you don't wrap a queue in a mutex. The queue API is already ISR-safe. Treat the queue as the channel.
  • Backpressure = queue fills up — in the queue demo, slow the consumer below the producer rate. The queue saturates at 16, producer's send returns errors. Either drop oldest, drop newest, or speed up consumer; never silently lose data.
  • Counting semaphore for pools, not for counting events — if you give faster than you take, count saturates at max and events are lost. Use a queue for event streams.
  • Priority inheritance only on mutexes — binary semaphores do NOT boost. If you protect a resource with a binary semaphore, you've shipped a priority-inversion bug.

API NAMES (FreeRTOS)

  • xSemaphoreCreateMutex() — mutex
  • xSemaphoreCreateBinary() — binary sem
  • xSemaphoreCreateCounting(max, initial)
  • xQueueCreate(len, itemSize)
  • ...FromISR variants for all of the above
  • portYIELD_FROM_ISR(woken) at end of ISR if any *FromISR returned woken=true

HAZARDS

  • Wrapping a queue in a mutex — redundant and a deadlock waiting to happen.
  • Binary sem to protect data — no inheritance, priority inversion incoming.
  • Forgetting to give back — leaks a slot in counting sem, deadlocks mutex.
  • Take in ISR — illegal; ISR cannot block.
  • Two mutexes, different order — classic deadlock. Always lock in same global order.
  • Big items in a queue — queue copies them. For large objects pass a pointer (and protect the buffer separately).
