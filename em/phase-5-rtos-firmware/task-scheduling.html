Task Scheduling — preemptive vs cooperative

Three tasks, three priorities, two scheduling policies. Watch the high-priority task slide into the CPU the instant it becomes ready — or wait politely, depending on the policy.

An RTOS scheduler answers one question a thousand times per second: "of all the tasks that are READY right now, which has the highest priority?" Under preemptive scheduling, the scheduler is allowed to interrupt a lower-priority task mid-instruction and switch to the higher-priority one. Under cooperative scheduling, it can only switch when the current task voluntarily yields (calls vTaskDelay, blocks on a queue, etc.). Preemptive guarantees response time for the highest-priority task; cooperative is simpler to reason about but a runaway low-priority task can starve everything. Rate-monotonic scheduling is a deceptively simple priority-assignment rule: shorter period → higher priority. For the arm, that means the 10 kHz current loop sits above the 1 kHz position loop sits above the 100 Hz comm task. Liu & Layland proved (1973) that under RMS, a set of N tasks is schedulable if total utilization stays under N·(2^(1/N) − 1), which converges to ~69% as N grows.

What to notice

  • Preemptive: HIGH always wins — the moment HIGH's period elapses, it preempts whatever is running. You can see MED segments get "sliced" by HIGH and resume after. That's a context switch.
  • Cooperative: HIGH waits for MED to yield — switch the policy. MED runs to completion (because it never calls vTaskDelay mid-job). HIGH's response time becomes "however long MED's longest run takes," and your control loop is suddenly at MED's mercy.
  • Rate-monotonic = shorter period wins — set HIGH period to 10 and MED period to 2. Now MED is the "real" high-priority task per RMS. If you don't re-prioritize, you've inverted the policy and the 2-ms-period task will miss its deadline. Always assign priority by period, not by "feels important."
  • Liu-Layland is sufficient, not necessary — Σ U ≤ N(2^(1/N)−1) guarantees schedulability under RMS but is conservative. A response-time analysis can show ~100% schedulability with hand-tuned priorities. Use Liu-Layland for a back-of-envelope sanity check.
  • LOW always starves under heavy RT load — if HIGH+MED utilization is 80%, LOW only gets 20% of CPU. Background logging, network heartbeat, etc., live at LOW. Plan accordingly.
  • "FreeRTOS is preemptive by default" — configUSE_PREEMPTION = 1. You can also set configUSE_TIME_SLICING = 1 so equal-priority tasks round-robin. Different policies live in the same scheduler.

Cheat sheet

SCHEDULABILITY

Utilization
U_i = C_i / T_i C = exec time, T = period
Total U
U = Σ C_i / T_i
Liu-Layland
U ≤ N·(2^(1/N) − 1) → 0.828 (N=2), 0.780 (N=3), 0.693 (N→∞)
EDF bound
U ≤ 1.0 Earliest-Deadline-First is optimal — uses 100%

PRIORITY ASSIGN

  • Rate-monotonic — shorter period = higher priority. Static, easy.
  • Deadline-monotonic — when deadline ≠ period, sort by deadline.
  • EDF — pick the task with closest deadline at runtime. Higher utilization but more overhead and harder to debug.
  • For the arm: current 10 kHz → P=highest, position 1 kHz → P=high, comms 100 Hz → P=med, logging 10 Hz → P=low.
  • Equal-priority tasks round-robin if time-slicing on, else first-ready runs to completion/yield.

WHAT GOES WRONG

  • Inverted priority by feels — "the UI is important to the user so it gets high priority." No. UI is event-driven, low priority. Control is hard real time.
  • Overlong "high-priority" task — if HIGH exec ≥ HIGH period, HIGH starves itself. Σ U includes itself.
  • Cooperative + no yield — a single loop forgetting vTaskDelay wedges the whole system.
  • Counting only RT tasks for Liu-Layland is correct, but make sure LOW gets non-zero CPU or it'll never complete.
  • Context-switch cost ignored — Liu-Layland assumes zero. In practice subtract ~2–5% for switch overhead.
