Debugging Tools — Pick the Right One for the Problem

A ladder from "easy + intrusive" to "hard + non-invasive." Reach for the lowest rung that will answer your question. Click a tool to see when to use it.

Embedded debugging has a ladder. printf is the bottom: anyone can use it, but it's slow, blocks the CPU, and stops working when the bug only happens at 20 kHz. SWO/ITM is the next rung: still text-based, but DMA'd out a dedicated pin at MHz rates with negligible overhead — perfect for tracing fast loops. A logic analyzer plugs into your digital lines and shows you what's happening on the bus at nanosecond resolution. An oscilloscope shows analog reality: actual voltages, gate-driver propagation delay, noise rides on the rail. A JTAG breakpoint halts the CPU and shows you everything — RAM, registers, call stack — but it stops time, which is useless for any timing-sensitive bug. Knowing which tool answers your question (and which would lie to you about it) is half of debugging.

Overhead vs visibility

What to notice

  • printf is a Heisenberg trap — printing inside a 20 kHz ISR slows that ISR enough to change behavior. The bug "disappears" with printf added, returns when removed. SWO/ITM via DMA avoids this.
  • A GPIO toggle is the simplest profiler — set a pin high at the start of your ISR, low at the end. Hook a scope. The pulse width = ISR execution time. Free, deterministic, sub-µs accurate.
  • Logic analyzer for protocols, scope for signal integrity — if you wonder "did the SPI message say what I expected", LA. If you wonder "is the rising edge clean or ringing", scope.
  • JTAG breakpoint freezes the world — useless for real-time bugs: the PWM keeps running, the motor keeps moving, the encoder keeps spinning, but your CPU is stopped. Coming back from a breakpoint in a motor controller usually means an overcurrent fault.
  • The bus sniffer is non-negotiable for distributed systems — a $20 USB-CAN dongle plus candump tells you exactly what crossed the bus. Tier 1 diagnosis for any "the joint is misbehaving" problem.
  • Always start by reproducing the bug on the bench — intermittent field bugs are 10× harder than reproducible bench bugs. Spend time on reproduction before tooling.

SWO/ITM SETUP (STM32)

  • Pin — PB3 (SWO) on most STM32; check your part's datasheet.
  • Speed — SWO at 2 MHz typical; can hit 20+ MHz.
  • API — ITM_SendChar() from core_cm4.h.
  • Toolchain — STM32CubeIDE / OpenOCD / J-Link Viewer all support.
  • Overhead — ~5 cycles per char, dropped if buffer full (non-blocking).
  • Format — plain ASCII; route to logger via printf retarget.

COMMON PITFALLS

  • Probing without grounding — scope probe ground clip skipped → measurement floats, looks like noise.
  • 10:1 probe set to 1:1 — readings are 10× off; double-check before declaring a problem.
  • Logic analyzer threshold wrong — 5 V logic with 3.3 V threshold (or vice versa) gives garbage decode.
  • SWO requires SWD (not JTAG-only) debugger — old ST-LINK V1 / cheap clones may not support.
  • Bus sniffer at wrong bitrate — silently drops every frame. Always confirm sniffer baud matches the bus.
  • Breakpoints in ISRs — when the CPU stops, the ISR doesn't return; the next interrupt is lost; system spirals. Use SWO instead.
