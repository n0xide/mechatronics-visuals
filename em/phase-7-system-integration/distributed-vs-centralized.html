Distributed vs Centralized Architecture

Two ways to build an N-joint robot. One MCU running everything (centralized) vs N small MCUs each running one joint (distributed). The bandwidth, latency, and maintainability tradeoffs flip dramatically.

Centralized means a single beefy MCU (or SBC) reads every encoder, runs every current loop, drives every gate driver. Pros: one codebase, one debug target, simple wiring philosophy ("everything to the brain"). Cons: every encoder + every gate driver has to physically reach that one board, so you're routing tens of high-speed signals across the chassis; one MCU failure kills the whole robot; the firmware is monolithic. Distributed means each joint has its own small MCU that closes the local loops, talking only summary state up the bus. Pros: short wires (encoder + driver live with the motor), independent failure domains, firmware modularity. Cons: more boards to design and stock, requires a real-time bus, harder global coordination. As N grows, distributed wins everywhere except cost-of-first-prototype.

What to notice

  • Centralized cable count explodes — drag N to 12. The centralized side has 12 encoders × 4 signals + 12 drivers × 8 signals = ~144 wires crossing the robot. The distributed side has 2 (CAN bus). Cable mass + flex life + EMI all matter on a real arm.
  • Centralized MCU saturates — at 20 kHz × N joints, each FOC iteration costs ~20 µs. With N=12 you need 12×20 µs = 240 µs per period vs a 50 µs deadline. The single MCU cannot service all loops in time.
  • Bus utilization stays low in distributed — even at N=24, each joint sends 16 bytes × 1 kHz = 16 kB/s = 128 kbps. Sum over 24 joints = 3 Mbps, well under CAN-FD's 5 Mbps data phase.
  • Centralized is fine for N ≤ 3 or so — a quadcopter has 4 ESCs (each is itself a tiny controller), a 2-wheel robot has 2 motors. At this scale, distributed adds overhead without benefit. Don't over-architect.
  • Distributed has versioning costs — if you flash joint J3 with new firmware but forget J5, you have a system with inconsistent behavior. Solve with: bootloader that checks compatibility on boot, version field in every message, automated fleet update tool.
  • Hybrid is real — many real robots: one host (Pi/Jetson) + smart motor controllers (ODrive, Moteus) per joint. ODrive already does FOC, so you talk to it over CAN at the velocity-loop tier. This is distributed at the joint level + centralized at the planning tier.

Cheat sheet

WHEN TO CENTRALIZE

  • N ≤ 3 actuators — overhead of distributed isn't worth it.
  • Co-located — all motors on one PCB, short signal runs.
  • Tight coupling — coordinated control (e.g. CoreXY where two motors blend into XY motion) is easier with shared state.
  • Prototyping — first proof-of-concept; switch to distributed once architecture is proven.

WHEN TO DISTRIBUTE

  • N ≥ 4 actuators with independent loops.
  • Physically spread out — encoders >30 cm from controller.
  • Motor noise — analog signals would have to cross noisy environment.
  • Failure isolation matters — safety-critical or expensive payload.
  • Scaling — plan to add more joints or sensors later.

COMMON PITFALLS

  • Putting the fast loop on the bus — kills the entire distributed-wins argument. Close locally, send summaries.
  • Forgetting bootloader strategy — N firmwares × M revisions = chaos without an OTA + version-pinning plan from day 1.
  • "It's just one more wire" — every centralized cable that crosses the chassis is a flex-life failure waiting to happen. Robots that flex break wires.
  • Heterogeneous joints, identical firmware — flash the same binary to all joints, override per-joint params (gear ratio, current limit) from a config file or fuse bits.
  • No bus sniffer in your debug kit — for distributed, a CAN analyzer (PCAN, Kvaser, or a $20 USB-CAN dongle + CANalyze) is non-negotiable.
