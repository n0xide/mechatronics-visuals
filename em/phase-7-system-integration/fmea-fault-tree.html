FMEA & Fault-Tree Analysis — finding failure paths before they find you

FMEA (Failure Mode and Effects Analysis) is bottom-up: list every component, ask "how can this fail?", score severity / occurrence / detection, action the high-RPN items. FTA (Fault-Tree Analysis) is top-down: pick a top hazard ("uncommanded motion"), break it into intermediate events via AND/OR gates, compute the probability from base-event rates. Together they're the safety-case backbone for ISO 26262 (auto), IEC 61508 (industrial), DO-178C (aero), and IEC 60601 (medical). This visual scores FMEA rows live, draws an editable fault tree, and walks the arm-6dof "uncommanded joint motion" case.

RPN = S × O × D (1-1000) Action threshold: RPN > 100 typical · > 50 for safety-critical FTA gate: AND multiplies, OR sums (small p) ASIL / SIL: A-D / 1-4 by severity·exposure·controllability PFH: probability of dangerous failure per hour Common-cause failure (CCF): one root → multiple "independent" branches

FTA — the top-down method

Start with the hazard (top event), use Boolean gates to break it into intermediate events, and stop at "base events" you can assign a numerical rate to. Then compute probabilities up the tree.

AND gate: P(AND) = P(A) · P(B) (only triggers if BOTH inputs occur) OR gate: P(OR) = P(A) + P(B) − P(A)·P(B) (≈ P(A) + P(B) for small p) Top event T comes from cut-sets — minimal combinations of base events that cause T. For our arm-6dof "uncommanded joint motion": T = (encoder-stale OR fw-latched) AND (watchdog-fail) AND (brake-release-fault OR MOSFET-shorted) Why this AND structure: defense-in-depth. Each layer (sensor, fw, watchdog, brake) is independent → only fails when ALL bypass-protections fail. AND gates are GOOD in safety design — they multiply tiny probabilities into tinier ones. Watch for common-cause failure (CCF): if a single root (shared PSU, shared MCU, shared firmware bug) feeds two "independent" branches, the AND silently becomes an OR. β-factor models account for this.

Worked example — arm-6dof-pa612 "uncommanded joint motion"

Top event (hazard)

The 6-DOF arm makes an unplanned motion that exceeds the SSM safety zone (per ISO 13855) with a human present. Severity assessment: S = 9 (potential injury at typical arm energies).

Fault tree decomposition

Top event T: "uncommanded joint motion" T ⇐ (motor energized when not commanded) AND (brake fails to hold) AND (watchdog fails to fire) L_motor ⇐ (firmware bug latches PWM high) OR (MOSFET driver fault) OR (encoder commands runaway) L_brake ⇐ (brake release stuck) OR (brake supply lost during motion) L_wd ⇐ (watchdog timer disabled in firmware) OR (watchdog hardware fault) Three-way AND for independent defense-in-depth: T = L_motor · L_brake · L_wd

Numerical example (typical rates)

P(firmware latch) = 1e-7 /h · P(MOSFET fault) = 5e-7 /h · P(encoder runaway) = 2e-6 /h L_motor ≈ 1e-7 + 5e-7 + 2e-6 = 2.6e-6 /h P(brake stuck) = 1e-6 /h · P(brake supply lost) = 5e-6 /h L_brake ≈ 6e-6 /h P(watchdog disabled in fw) = 1e-6 /h · P(watchdog hw fault) = 1e-5 /h L_wd ≈ 1.1e-5 /h T = L_motor · L_brake · L_wd = 2.6e-6 · 6e-6 · 1.1e-5 = 1.7e-16 /h MTBF = 1/T ≈ 6e15 h (astronomical — really limited by common-cause) PFH_d category: ASIL D (PMHF target < 10⁻⁸ /h) — well within budget; the AND-of-three structure puts the calculated rate 8 orders below the ceiling

This is why brake + motor + watchdog are independent: knock out any one of these, even a faulty firmware that latches PWM high or a stuck-on MOSFET — the brake still holds the joint. Three layers of defense = three multiplied probabilities = vanishingly rare top event.

What kills this analysis (common-cause)

If the brake and motor share a single 24 V rail (one PSU), a PSU droop event fails both at once. The AND becomes effectively serial: T = P(PSU droop) = 1e-6 /h. MTBF = 114 years. Add a second backup rail for the brake → restore independence.

Common pitfalls

  • Score inflation / deflation — without anchor examples, two engineers will score the same failure as RPN 30 and RPN 300. Always use a calibration table with specific examples for each S, O, D level.
  • RPN tunnel vision — fixing high-RPN items only. AIAG-VDA 2019 deprecated raw RPN; recommends Action Priority (AP) which considers each axis. A failure with S=10/O=1/D=1 has RPN=10 but you still need to mitigate it (cannot ignore catastrophic effects, however rare).
  • Forgetting CCF — shared power, shared MCU, shared firmware, shared sensor pulled from same lot. Apply β-factor: P(CCF) = β · P(single failure), β = 1-10 % typical.
  • Static FMEA at design freeze — FMEA is a living document. Update after every field failure, every ECO, every supplier change.
  • Fault tree without environmental events — temperature extreme, EMI, vibration, ESD all introduce failure modes not visible at room-temp bench. Include "environmental" base events with rates from MIL-HDBK-217 or FIDES.
  • "Detection" credit before testing it works — score D=2 only if the detection mechanism has been tested under the actual fault. Many BIT (built-in-test) routines miss the very faults they're meant to catch.
  • Inherited assumptions in fault tree — base-event rates inherited from a previous project may not apply (different vendor, different stress profile, different duty cycle). Re-evaluate.
  • Confusing FMEA with FMECA — FMECA adds Criticality analysis (often a more rigorous version of S·O). Both are valid; pick one and use consistently.
