Hardware-in-the-Loop (HiL) Architecture

HiL is the test bench every safety-critical embedded engineer reaches for after unit tests but before physical-rig testing. The MCU under test runs its real firmware. The mechanical / physical world it controls is simulated on a separate, faster computer that exchanges I/O with the MCU in real time. Result: thousands of test scenarios per day, including fault injection that would damage real hardware.

Real-time loop: typ 1-10 kHz, < 1 ms latency Plant model: simulation of motors, batteries, environment Faults: stuck sensor, open phase, short, voltage sag, all reproducible Used in: auto/aero industry standard, ISO 26262 mandates

How it works — the signal flow

  • Plant model on the simulator computes physical quantities: motor currents, voltages, encoder positions, temperatures. Updates at 1-10 kHz.
  • I/O bridge (real-time card with DACs + ADCs + digital I/O) converts model state into analog/digital signals the DUT sees as "real sensors". DAC outputs current, ADCs read what DUT commands.
  • DUT runs the production firmware unchanged. From its perspective, it's connected to real hardware.
  • DUT outputs (PWM, CAN commands, GPIO) flow back through the I/O bridge into the simulator, closing the loop.
  • Test sequencer on the simulator side scripts scenarios: ramp the load, inject a sensor failure, drop the supply voltage. Logs everything for analysis.

The math behind real-time

A HIL simulator must update faster than the DUT's control loop sees the world. If the DUT closes a 1 kHz current loop, the plant model must update at > 10 kHz, ideally 20-100 kHz. This requires:

  • Hard real-time OS: VxWorks, QNX, RT-Linux (PREEMPT_RT), or bare-metal on FPGA
  • Bounded interrupt latency: typically < 10 µs jitter
  • Fixed-step solver: ODE solver runs at the loop rate, no adaptive timestep
  • FPGA accelerator for fast dynamics: motor + inverter modeled at 1 MHz on FPGA, slower dynamics on CPU

Worked example — arm-6dof-pa612 joint controller HIL setup

The goal

Validate the joint-controller firmware against 500 test scenarios before deploying to a $50k physical robot. Each scenario takes < 30 s on the HIL bench; a full regression sweep runs in 4 hours overnight.

Test scenarios run nightly

  1. Step inputs at every joint, validate settling time and overshoot
  2. Sinusoidal trajectory tracking at 0.5, 1, 2, 5 Hz; measure phase lag
  3. Disturbance rejection: inject sudden 5 N·m torque pulse
  4. Sensor fault: open encoder phase A; verify fail-safe stops within 50 ms
  5. Bus brownout at random points in trajectory; verify clean restart
  6. Stress: max-rate command stream over CAN at 1 kHz for 1 hour; check no deadline misses
  7. Collision: simulated end-effector contact with virtual wall; verify impedance limits

Cost: ~$15k HIL bench + 1 month engineering. Saved: 6 months of physical-robot debugging + 3 hardware replacements at $8k each.

Common pitfalls

  • Model fidelity — your plant model must include real-world non-idealities: friction, backlash, sensor noise, computational delays. A too-clean model passes tests that real hardware fails.
  • I/O latency — DAC settle time, ADC sample-and-hold, bus arbitration. Total round-trip from sim output → DUT input → DUT output → sim input should be < 1 PWM period.
  • Real-time guarantees — Windows + USB DAQ does not count as real-time. You'll see correct mean behavior but missed worst-cases.
  • Validation of the model itself — HIL tests prove the firmware matches the model, not reality. Periodic correlation with physical-rig tests is mandatory.
  • Test coverage — 1000 random scenarios isn't comprehensive. Use combinatorial test design (pair-wise) or model-based test generation.
  • Versioning — HIL scenarios are themselves code. Treat the test scripts + plant model + firmware as a versioned set; one regression test failure must reproduce exactly later.
