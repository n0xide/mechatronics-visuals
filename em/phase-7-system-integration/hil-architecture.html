Hardware-in-the-Loop (HIL) Architecture

HIL is the test bench every safety-critical embedded engineer reaches for after unit tests but before physical-rig testing. The MCU under test runs its real firmware. The mechanical / physical world it controls is simulated on a separate, faster computer that exchanges I/O with the MCU in real time. Result: thousands of test scenarios per day, including fault injection that would damage real hardware.

Plant rate: 10-100× the DUT control rate Round-trip latency: must fit inside one control period Faults: stuck sensor, open phase, short, voltage sag — reproducible Used in: automotive (ISO 26262), aero (DO-178C), rail

The math behind real-time

Control period: T_ctrl = 1 / f_ctrl Round-trip latency: t_RT = t_DAC_settle + t_ADC_sample + t_bus_in + t_DUT_compute + t_bus_out + t_plant_step Real-time requirement: t_RT < T_ctrl (strict) t_RT < 0.5 · T_ctrl (recommended — leaves headroom for jitter) Plant fidelity: f_plant ≥ 10 · f_ctrl (Nyquist + safety margin) When t_RT > T_ctrl: drop control freq, simplify plant, or offload fast dynamics to FPGA. Common split: CPU at 100 µs step, FPGA at 1 µs step for inverter PWM + current loop.

How it works — the signal flow

  • Plant model on the simulator computes physical quantities: motor currents, voltages, encoder positions, temperatures. Updates at 10-100× the DUT control rate.
  • I/O bridge (real-time card with DACs + ADCs + digital I/O) converts model state into analog/digital signals the DUT sees as "real sensors." DACs drive the DUT's sensor pins; ADCs read what the DUT commands.
  • DUT runs the production firmware unchanged. From its perspective, it's connected to real hardware.
  • DUT outputs (PWM, CAN, GPIO) flow back through the I/O bridge into the simulator, closing the loop.
  • Test sequencer on the simulator side scripts scenarios: ramp the load, inject a sensor failure, drop the supply voltage. Logs everything for analysis.

Worked example — arm-6dof-pa612 joint controller HIL setup

The goal

Validate the joint-controller firmware against 500 test scenarios before deploying to a $1.5k prototype arm. Each scenario takes < 30 s on the HIL bench; a full regression sweep runs overnight.

Test scenarios run nightly

  1. Step inputs at every joint, validate settling time and overshoot
  2. Sinusoidal trajectory tracking at 0.5, 1, 2, 5 Hz; measure phase lag
  3. Disturbance rejection: inject sudden 5 N·m torque pulse
  4. Sensor fault: open encoder phase A; verify fail-safe stops within 50 ms
  5. Bus brownout at random points in trajectory; verify clean restart
  6. Stress: max-rate command stream over CAN at 1 kHz for 1 hour; check no deadline misses
  7. Collision: simulated end-effector contact with virtual wall; verify impedance limits

Cost: ~$8k DIY HIL bench (PXIe + FPGA card) or ~$15k turnkey (Speedgoat baseline). Saves ~6 months of physical-robot debugging + several joint replacements after fault-injection-induced damage.

Common pitfalls

  • Model fidelity — your plant model must include real-world non-idealities: friction, backlash, sensor noise, computational delays. A too-clean model passes tests that real hardware fails.
  • I/O latency — DAC settle time, ADC sample-and-hold, bus arbitration. Total round-trip from sim output → DUT input → DUT output → sim input should fit inside one PWM period.
  • Real-time guarantees — Windows + USB DAQ does not count as real-time. You'll see correct mean behavior but missed worst-cases. Use PREEMPT_RT Linux or a deterministic kernel (QNX / VxWorks).
  • Validation of the model itself — HIL tests prove the firmware matches the model, not reality. Periodic correlation with physical-rig tests is mandatory.
  • Test coverage — 1000 random scenarios isn't comprehensive. Use combinatorial test design (pair-wise) or model-based test generation.
  • Versioning — HIL scenarios are themselves code. Treat the test scripts + plant model + firmware as a versioned set; one regression failure must reproduce exactly later.
  • Numerical instability at the step boundary — stiff plants (high-frequency dynamics, low damping) require small enough integrator steps to stay stable. Watch for explosive divergence — usually means step too large.
