ROS 2 DDS QoS Profiles — getting the right reliability / latency tradeoff

ROS 2 doesn't have built-in queues or fan-out logic — it delegates all of that to DDS (Data Distribution Service), the OMG real-time pub/sub standard. Every topic in ROS 2 has a QoS profile attached: a bundle of policies controlling how messages are delivered, stored, and dropped. Get them wrong and your publisher and subscriber will silently fail to connect; get them right and you can tune throughput, latency, and durability per topic. This visual breaks down the 6 fields you'll touch day-to-day (Reliability, Durability, History+Depth, Deadline, Lifespan, Liveliness), then offers a use-case-to-profile picker.

Standard: OMG DDS-RTPS over UDP Default RMW: rmw_fastrtps (Foxy+), rmw_cyclonedds (newer) Gotcha: incompatible QoS → silent no-connection Compatibility rule: subscriber-requested guarantee ≤ publisher-offered guarantee (pub must be at least as strong)

The 6 QoS fields you actually configure

1. Reliability

RELIABLEretransmit losses; TCP-like
BEST_EFFORTfire and forget; UDP-like

Sensor streams = BEST_EFFORT (lossy is fine, latest matters). Commands, state machines = RELIABLE.

2. Durability

VOLATILEno history for late joiners
TRANSIENT_LOCALpublisher keeps last N for late subs

Use TRANSIENT_LOCAL for "static" topics — TF static, robot description, parameters — so subscribers that start later still get the last value.

3. History

KEEP_LAST (depth N)ring buffer of size N
KEEP_ALLunbounded until resource_limits

Default is KEEP_LAST depth 10. Set depth=1 for "latest only" (e.g., latest velocity command). Set higher for command queues.

4. Deadline

durationmax gap between publishes

Publisher promises to send at least this often. If gap exceeded, both pub and sub get a "deadline missed" callback. Tells you a sensor died.

5. Lifespan

durationmax message age

Messages older than this are dropped before being delivered. Stops stale commands from being applied after a comm hiccup.

6. Liveliness

AUTOMATICheartbeats sent by DDS automatically
MANUAL_BY_TOPICpublisher must call assert_liveliness()

Combined with lease_duration: if no heartbeat for that long, subscribers get "publisher lost" callback. Watchdog mechanism.

The compatibility rule (a.k.a. why your nodes don't talk)

For each field, the subscriber's requested value must be "less demanding" than the publisher's offered value, or DDS will refuse to connect them. Common cases:

Publisher offersSubscriber requestsMatch?
RELIABLERELIABLE or BEST_EFFORTYES (publisher meets both)
BEST_EFFORTRELIABLENO — sub wants stronger guarantee than pub offers
TRANSIENT_LOCALVOLATILE or TRANSIENT_LOCALYES
VOLATILETRANSIENT_LOCALNO
Deadline 10msDeadline 100msYES (pub more aggressive than sub asks)
Deadline 100msDeadline 10msNO — sub demands faster than pub promises

The painful part: this fails silently. Your ros2 topic list shows the topic, but ros2 topic echo outputs nothing. Diagnose with ros2 topic info /topicname --verbose — it lists each pub/sub with its QoS, and the lines with mismatches.

How to set QoS in code

C++ (rclcpp)

auto qos = rclcpp::QoS(rclcpp::KeepLast(5))
  .best_effort()
  .durability_volatile();

pub_ = create_publisher<sensor_msgs::msg::Image>("/camera/image", qos);
sub_ = create_subscription<sensor_msgs::msg::Image>("/camera/image", qos, callback);

Python (rclpy)

from rclpy.qos import QoSProfile, ReliabilityPolicy, DurabilityPolicy, HistoryPolicy

qos = QoSProfile(
    reliability=ReliabilityPolicy.BEST_EFFORT,
    durability=DurabilityPolicy.VOLATILE,
    history=HistoryPolicy.KEEP_LAST,
    depth=5)

self.pub = self.create_publisher(Image, '/camera/image', qos)

Launch file or yaml override

/camera_node:
  ros__parameters:
    qos_overrides:
      /camera/image:
        publisher:
          reliability: best_effort
          history: keep_last
          depth: 5

The hidden gotchas

  • rosbag2 default uses RELIABLE — but most sensor topics are BEST_EFFORT. Recording from a sensor topic with default bag QoS fails silently. Pass --qos-profile-overrides-path qos.yaml or use --all + --include-hidden-topics with override.
  • RViz uses RELIABLE by default for most displays — if your camera publishes BEST_EFFORT, RViz won't render. The display has a Reliability dropdown — switch to "Best Effort."
  • Default depth 10 too small for high-rate sensors — 200 Hz IMU into a 50 Hz consumer with depth 10 → consumer pulls 50/s, ~150/s overflow the ring buffer and get dropped (~75 %). Either lower publisher rate or raise consumer's depth.
  • TRANSIENT_LOCAL is per-publisher, not shared — restarting a publisher loses its history. The "latched topics" pattern from ROS 1 is approximated by TRANSIENT_LOCAL but with caveats.
  • Different RMWs interoperate but have quirks — Fast-DDS ↔ Cyclone DDS works but with subtle differences in discovery timing and multi-NIC behavior. Force one RMW across your whole system with RMW_IMPLEMENTATION=rmw_cyclonedds_cpp in ~/.bashrc.
  • Discovery storms in large systems — every node broadcasts discovery packets. With >50 nodes on shared multicast, this saturates the network. Use Discovery Server (fastdds discovery) or Cyclone DDS's NetworkInterface config.

Debugging QoS mismatches in the wild

  1. ros2 topic info /topicname --verbose — lists each pub/sub with full QoS dump. Look for fields that differ.
  2. ros2 doctor --report — flags some QoS mismatches automatically.
  3. RCUTILS_LOGGING_SEVERITY=DEBUG ros2 run ... — DDS layer logs "incompatible QoS" with field name and offered/requested values.
  4. Check logs from BOTH sides — sometimes only one side prints the warning.
  5. If using a Discovery Server, verify it sees both ends with fastdds discovery -i 0 -l 0.0.0.0.
