System Block Diagram — Multi-Axis Robot Arm

Click any block to see its responsibilities, interfaces, and where its messages flow. This is the canonical mechatronic system: host brain talks over one bus to many smart-joint slaves.

A robot arm is not "one big controller running everything." It's a federation: a high-level computer that knows about the world and plans trajectories (ROS 2 on a Raspberry Pi 5), a deterministic bus that carries those plans down to each joint (CAN-FD), and one smart-controller per joint that closes the fast current/velocity/position loops locally (STM32 + gate driver + motor + encoder). The host never sees the 20-kHz current loop — it only sees the 1-kHz joint state. Each joint never sees the trajectory planner — it only sees its target angle and speed. This separation of timescales (planning Hz, joint kHz) is the entire architectural rationale.

What to notice

  • Separation of timescales — host plans at 10–100 Hz, sends joint targets at 1 kHz over CAN-FD, joints close the current loop at 20 kHz locally. The fast loops never cross the bus.
  • The bus is the contract — pick CAN-FD and a message schema (DBC or ad-hoc), and the host team and the joint-firmware team can work independently. Bus failures become well-defined: missing heartbeat, CRC error, out-of-range value.
  • Termination matters — exactly two 120 Ω resistors, one at each physical end of the bus. Three resistors → over-termination → comms fail. One resistor → reflections → comms fail intermittently.
  • Power is its own topology — 48 V motor rail must be physically separate from 3.3 V logic with a star ground. Otherwise motor commutation noise rides on your ADC reference and current measurements look like trash.
  • Smart joints scale — adding J7 (wrist roll) means: new STM32 board, new CAN ID, add stub to bus, declare in URDF. No change to existing joints. This is the architectural win over a "one big MCU" design.
  • The encoder is in the loop, not on the bus — joint controller reads encoder over local SPI at 20 kHz. Sending raw encoder counts over CAN every iteration would saturate the bus and add tens of µs of latency. Send state (position/velocity) at 1 kHz instead.

Cheat sheet

ARM PROJECT STACK

  • Host — Raspberry Pi 5, Ubuntu 22.04, ROS 2 Humble.
  • Bus — CAN-FD, 1 Mbps/5 Mbps, MCP2518FD HAT on Pi.
  • Joint MCU — STM32G431 (FPU + HRTIM + fast ADC).
  • Driver — DRV8316 or B-G431B-ESC1 dev board.
  • Encoder — AS5048A 14-bit magnetic SPI.
  • Frame — URDF + TF2 tree, every link gets a frame_id.

LOOP RATES (RULE OF THUMB)

Trajectory
10–100 Hz (host)
Joint state pub
1 kHz (over CAN-FD)
Position loop
250–500 Hz (joint MCU)
Velocity loop
1–2 kHz (joint MCU)
Current loop
10–20 kHz (joint MCU, local)

COMMON PITFALLS

  • Sending the fast loop over the bus — never. Each tier closes locally; only state and targets cross.
  • Mid-bus termination — 120 Ω goes at endpoints only. Stubs to nodes ≤ 30 cm.
  • Shared ground between motor and logic — separate them, tie at one star point.
  • No URDF / frame discipline — every sensor and joint must have a documented frame; otherwise TF tree breaks and MoveIt refuses to plan.
  • Hardcoding CAN IDs in N firmwares — one shared message header, generated from a DBC file.
