SLAM & Occupancy Grids — Build a map while localizing in it

Simultaneous Localization And Mapping is the chicken-and-egg problem of robotics: to map the environment you need to know where you are; to know where you are you need a map. SLAM solves both at once, incrementally, by treating the robot pose AND the landmark positions as joint unknowns to be estimated. This visual walks through occupancy-grid SLAM with simulated laser scans + a loop-closure event.

The SLAM problem statement

Given: noisy measurements z₁:t (sensor observations) and noisy controls u₁:t (odometry) Find: robot pose x_t AND map m (landmarks or grid cells) Bayesian formulation: p(x_t, m | z₁:t, u₁:t) Both x and m are unknowns. Sensors observe both jointly. Classical decomposition (Murphy, 1999): p(x_1:t, m | z, u) = p(m | x_1:t, z) · p(x_1:t | z, u) → "Mapping with known poses" × "Localization with known map"

Occupancy-grid SLAM (the simplest concept)

Divide the 2D environment into a fine grid (typically 5-10 cm cells). For each cell store the probability P(occupied). Each laser scan adds evidence:

  • Cells along the ray (free space) → decrease P(occ)
  • Cell at the ray hit point → increase P(occ)
  • Cells beyond the hit → unchanged (unknown)

This is "inverse sensor model" mapping. The math is simple log-odds:

log-odds: l(c) = log( P(occ) / (1 - P(occ)) ) For each scan ray: l_new(c) = l_old(c) + l_inv_sensor(c) Empty cell update: Δl = −0.4 (a log-odds increment; multiplies the occupancy odds by e−0.4 ≈ 0.67) Hit cell update: Δl = +0.85 (multiplies the odds by e0.85 ≈ 2.34) Convert back: P(occ) = 1 / (1 + exp(-l))

Pose-graph SLAM (modern approach)

Modern SLAM (ORB-SLAM3, Cartographer, LIO-SAM) uses a pose graph:

  • Nodes: robot poses at discrete timestamps (x_1, x_2, ..., x_t)
  • Edges (odometry): constraint between consecutive poses, from odometry/IMU/wheel-velocity
  • Edges (loop closure): constraint between non-consecutive poses, from place recognition (e.g., scan matching)
  • Optimization: find x_1:t that minimizes weighted sum of edge errors

Loop closure — the magic moment

Why it matters

Odometry alone has unbounded drift — after 100 meters of motion, a 1% wheel-slip can put you 1 meter off, and the map is smeared. Loop closure happens when the robot recognizes "I've been here before" — by matching current laser scan or camera view against an old one. This injects a global constraint: pose_now must equal (approximately) pose_then.

The pose-graph optimizer (g2o, GTSAM, Ceres) propagates this correction backward through all intermediate poses. Suddenly the smeared map snaps into focus — walls align, the loop closes geometrically.

The math behind GraphSLAM (sketch)

Each edge contributes a residual: r_ij = z_ij − h(x_i, x_j) where z_ij is the measured transform i→j, h is the predicted transform Total cost: F(X) = Σ r_ij^T · Ω_ij · r_ij (Ω = information matrix = inv covariance) Minimize via Gauss-Newton / Levenberg-Marquardt: X_new = X − (J^T·Ω·J)^-1 · J^T·Ω·r Sparse matrices (most poses aren't connected) make this scalable to 10k+ poses.

Common pitfalls

  • Loop closure false positives — two visually similar but actually-different places (long corridors, repeating patterns) cause catastrophic map corruption. Use geometric verification + delayed acceptance to filter.
  • Symmetric environments — featureless rooms or symmetric layouts give pose ambiguity. SLAM diverges silently.
  • Aggressive motion + rolling-shutter cameras — image distortion makes feature matching unreliable. Use global-shutter cameras for visual SLAM.
  • Dynamic objects (people, vehicles) — appear as moving "ghosts" in the map. Modern SLAM masks dynamic regions via DBOW3 + semantic segmentation.
  • Initialization in monocular SLAM — scale is unknown from a single view; needs translation motion (not pure rotation) to bootstrap.
  • Loop-closure search cost — comparing current frame against all past frames is O(N). Use hierarchical visual vocabulary (DBoW3) for O(1) candidate retrieval.
  • Computational budget — Cartographer + 64-beam lidar at 10 Hz needs ~4 cores. Plan for it.

Worked example — SLAM for a warehouse robot

Setup

4-wheel differential-drive robot in a 40m × 60m warehouse. Goal: build a 2D map of the warehouse + localize within ±10 cm during operation. Constraints: under $5k of sensors, must work in real time on an embedded PC.

Expected performance

~5 cm localization accuracy. Loop closure triggers automatically at recognized scan matches. Full map of 40×60 m built in 5-10 minutes of teleoperation. After mapping, localization-only mode runs at < 10% CPU. Drift between loop closures < 0.5% of distance traveled (10 cm per 20 m).
