ROS 2 Quick Reference

ROS 2 is the robotics middleware running on every modern robot — autonomous cars, arms, drones. The conceptual model is the same as ROS 1 (nodes / topics / services / actions) but the wire protocol is DDS, and that brings QoS profiles, discovery, lifecycle nodes. This card is the everyday CLI + Python/C++ + launch-file reference.

Current LTS: Humble (2022 → 2027) Wire: DDS (Fast-DDS, Cyclone DDS) Build: colcon, ament_cmake / ament_python Languages: Python (rclpy) + C++ (rclcpp)

QoS profiles — the DDS gift (and trap)

Every topic publisher and subscriber has a Quality-of-Service profile. They must be compatible for the connection to form. The common settings:

QoS fieldValuesWhat it controls
ReliabilityBEST_EFFORT or RELIABLERetransmit on packet loss? (Reliable = TCP-like; Best-effort = UDP-like)
DurabilityVOLATILE or TRANSIENT_LOCALDoes a publisher remember the last message for late-joining subscribers?
HistoryKEEP_LAST(n) or KEEP_ALLHow many old messages buffered
Depthinteger (e.g., 10)Buffer size for KEEP_LAST
DeadlinedurationMax time between consecutive publishes; missed = trigger callback
LifespandurationHow long a published message stays valid
LivelinessAUTOMATIC or MANUALHow publisher signals "I'm alive"

The QoS compatibility trap

If publisher is RELIABLE but subscriber is BEST_EFFORT — INCOMPATIBLE. Connection silently fails. ros2 topic info -v shows the QoS, and the offending mismatch.

Most-common-mistake: high-rate sensor (camera/lidar) publishing as BEST_EFFORT (default), then trying to subscribe with the default RELIABLE in rviz2 — sees no data. Set rviz topic reliability to BEST_EFFORT.

Minimal Python publisher (rclpy)

import rclpy
from rclpy.node import Node
from std_msgs.msg import String

class MyPub(Node):
    def __init__(self):
        super().__init__('my_pub')
        self.pub = self.create_publisher(String, 'chat', 10)
        self.timer = self.create_timer(1.0, self.tick)
        self.i = 0

    def tick(self):
        msg = String()
        msg.data = f'hello #{self.i}'
        self.pub.publish(msg)
        self.get_logger().info(f'published: {msg.data}')
        self.i += 1

def main():
    rclpy.init()
    rclpy.spin(MyPub())
    rclpy.shutdown()

if __name__ == '__main__':
    main()

Minimal Python subscriber

import rclpy
from rclpy.node import Node
from std_msgs.msg import String

class MySub(Node):
    def __init__(self):
        super().__init__('my_sub')
        self.sub = self.create_subscription(
            String, 'chat', self.cb, 10)

    def cb(self, msg):
        self.get_logger().info(f'got: {msg.data}')

def main():
    rclpy.init()
    rclpy.spin(MySub())
    rclpy.shutdown()

Minimal launch file (Python)

from launch import LaunchDescription
from launch_ros.actions import Node

def generate_launch_description():
    return LaunchDescription([
        Node(
            package='my_pkg',
            executable='my_pub',
            name='publisher_a',
            parameters=[{'rate_hz': 1.0}],
            remappings=[('chat', '/topic_a')],
        ),
        Node(
            package='my_pkg',
            executable='my_sub',
            name='subscriber_a',
            remappings=[('chat', '/topic_a')],
        ),
    ])

TF2 — the coordinate frame tree

TF2 manages all frames in the robot: map → odom → base_link → joint frames → camera frames. Each transform is a 6-DOF pose between two frames, published as a TF message.

// Lookup transform in Python
from tf2_ros import Buffer, TransformListener
import rclpy

self.tf_buffer = Buffer()
self.tf_listener = TransformListener(self.tf_buffer, self)
# ...
try:
    t = self.tf_buffer.lookup_transform(
        'map', 'base_link', rclpy.time.Time())
    print(t.transform.translation.x, ...)
except Exception as e:
    self.get_logger().warn(f'TF lookup failed: {e}')

Debugging recipes

"My subscriber isn't receiving anything"

  1. ros2 topic list — does the topic exist?
  2. ros2 topic info /topic -v — pubs + subs + QoS shown?
  3. ros2 topic echo /topic — does data flow when you watch?
  4. Check QoS mismatch in topic info output.
  5. Check namespace remapping in launch file.
  6. Check DDS interface (Cyclone DDS may need ROS_DOMAIN_ID match).

"My launch file has a node that immediately exits"

  1. Launch with output='screen' to see stderr.
  2. ros2 run my_pkg my_node directly outside launch to see crash.
  3. Check exception in Python — most likely missing parameter or wrong message type.
  4. Check that executable name in setup.py matches what launch file references.

"TF tree has gaps"

  1. ros2 run tf2_tools view_frames generates a PDF of the tree.
  2. Look for orphaned frames (not connected to map or world).
  3. Check broadcast timing — TF lookups fail if no transform within ~0.1 s.
  4. Static transforms (URDF) need robot_state_publisher + joint_state_publisher running.

Performance tips

  • Use Best-effort QoS for sensor streams — saves CPU, drops gracefully on overload.
  • Set History to KEEP_LAST(1) for high-rate sensors — don't buffer old data.
  • Avoid std::cout in callbacks — use get_logger() which can be filtered. cout serializes.
  • Profile with ros2 topic hz + top — identify whether your bottleneck is rate, payload, or CPU.
  • For heavy compute (perception): separate Composer process. Components in shared process avoid serialization between nodes (intra-process communication).
  • Cyclone DDS generally outperforms Fast-DDS on Linux. Try switching if hitting bandwidth limits.
